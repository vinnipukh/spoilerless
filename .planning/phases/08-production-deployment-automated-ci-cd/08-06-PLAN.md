<objective>
Add a cache-aside layer in front of `GET /api/series/{series_id}/graph`, the
one graph-read endpoint, using the shared Redis client the rate-limiting plan
already created. Cache keys include the effective spoiler boundary and user,
so a boundary change alone always misses correctly with no explicit
invalidation needed; explicit invalidation covers writes that change graph
content at a fixed boundary.

Purpose: Reduce repeated Neo4j reads for the same spoiler-safe graph view
without ever risking a stale response across a content-changing write.
Output: Redis-cached graph reads with correct, write-triggered invalidation.
</objective>

    - Test: when get_settings().redis_url is empty, get_cached_graph always returns None and set_cached_graph is a no-op — the endpoint still returns correct data by falling through to Neo4j.

  <action>
    Create backend/app/cache/graph_cache.py: a key-builder
    `_cache_key(series_id: str, effective_boundary: int, user_id: str |
    None) -> str` returning
    `f"graph:{series_id}:{effective_boundary}:{user_id or 'anon'}"`;
    `async def get_cached_graph(series_id, effective_boundary, user_id) ->
    dict | None` that returns `None` immediately when
    `get_settings().redis_url` is empty, else calls `get_redis().get(key)`
    and `json.loads`s the value if present (wrap the Redis call in a
    try/except that returns `None` on any connection error — a cache
    failure must never surface as a request failure, per the "cache is a
    performance layer, not a hard dependency" truth this plan records);
    `async def set_cached_graph(series_id, effective_boundary, user_id,
    response: dict, ttl_seconds: int = 300) -> None` that
    `SETEX`s the JSON-serialized response (same empty-redis_url and
    error-swallowing guards); `async def invalidate_series(series_id: str)
    -> None` that uses `get_redis().scan_iter(match=f"graph:{series_id}:*")`
    to find and delete every cached key for that series in one pass
    (coarse per-series invalidation — correct and simple, since precisely
    tracking which (boundary, user) combinations a given write affects
    would require re-deriving GraphService's own visibility logic a second
    time; over-invalidating a series' cache on any of its writes is safe,
    under-invalidating is not).

    In backend/app/api/graph.py's `get_graph`, after computing `effective`
    and before calling `service.fetch_graph(...)`, check
    `get_cached_graph(series_id, effective, user["id"] if user else None)`
    and return it directly (as a `GraphResponse.model_validate(cached)`) on
    a hit; on a miss, call `fetch_graph` as today, then
    `set_cached_graph(series_id, effective, user_id, result.model_dump(mode="json"))`
    before returning it.

| T-08-06-02 | Denial of Service | Redis outage taking down the graph endpoint | low | mitigate | get_cached_graph/set_cached_graph swallow connection errors and fall through to Neo4j; caching is additive, never a hard dependency |
