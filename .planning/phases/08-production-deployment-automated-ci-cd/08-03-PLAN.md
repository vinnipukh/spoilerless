<objective>
Introduce a `role` field on the user record and enforce it on the two write
surfaces that mutate the shared canonical graph without per-user isolation —
candidate review (approve/reject/edit) and ChangeSet confirmation — plus
admin-gate the now-secondary `/api/settings/llm` endpoint per AUTH-04. Closes
the "no role infrastructure exists" gap PROJECT.md's Key Decisions and
docs/PROBLEMS.md #2 (anonymous candidate-approve = graph poisoning) flag,
scoped exactly to REQUIREMENTS.md's AUTH-03 wording (candidate review +
ChangeSet approval endpoints — not the separate revision-revert endpoint,
which is Phase 9/PROB-01 scope).

Purpose: Only a trusted operator-designated admin can commit a candidate
claim or an AI-proposed ChangeSet to the shared graph every visitor sees.
Output: Enforced admin role on three route groups; no self-service admin
grant path exists.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Authenticated non-admin user <-> shared canonical graph mutation endpoints | Any logged-in Google account today can promote a candidate or confirm a ChangeSet; this plan closes that gap |
| Login flow (Google-attested email) <-> role assignment | Role is derived only from a server-controlled env var checked against a verified email, never client input |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-03-01 | Elevation of Privilege | Anonymous/any-user candidate approval = graph poisoning (docs/PROBLEMS.md #2) | critical | mitigate | require_admin gate on approve/reject/edit |
| T-08-03-02 | Elevation of Privilege | Any user confirming an AI-proposed ChangeSet against the shared graph | high | mitigate | require_admin gate on confirm_change_set |
| T-08-03-03 | Elevation of Privilege | Self-service admin grant via a crafted request body | high | mitigate | role is never read from any request body; GoogleAuthRequest's extra="forbid" rejects unknown fields, and no route accepts a role parameter |
| T-08-03-04 | Tampering | Shared LLM settings hijack to an attacker base_url (docs/PROBLEMS.md #5, residual after BYOK) | medium | mitigate | /api/settings/llm now admin-only; the SSRF surface shrinks to a trusted operator's own choice |
| T-08-03-05 | Repudiation | No log of who granted/removed an admin role | low | accept | Role changes derive automatically from ADMIN_EMAILS at every login; no separate grant action exists to audit, and this milestone does not add an admin-action audit trail |

</threat_model>
