PRIMARY PRODUCT GOAL

Add a conversational interface where the authenticated user can ask questions
about the selected television series.

The assistant must:
- answer using only graph information visible up to the user's currently watched
  season and episode
- retrieve relevant Characters, Events, relationships, Claims, EvidenceFragments
  and Sources
- ground answers in Claim/Evidence/Source records
- provide clickable citations
- highlight relevant graph nodes and edges
- clearly say when the watched portion does not contain enough evidence
- never hint that hidden future information exists
- never reveal future character names, relationship types, counts or IDs
- support continued conversations
- support safe graph modifications through structured tools
- update the visible graph after an approved modification

The assistant should feel like an intelligent graph research and editing agent,
not a generic chatbot added beside the graph.

CRITICAL ARCHITECTURAL RULE

The LLM must never receive unrestricted Neo4j access.

Do not:
- give the model a raw Neo4j driver
- allow the model to execute arbitrary Cypher
- send the database schema and ask it to freely generate Cypher
- execute Cypher strings returned by the model
- trust frontend-provided visibility boundaries
- rely on the model to remember spoiler rules
- rely on system-prompt instructions as the only security boundary

The LLM may only use allowlisted, typed backend tools.

Every retrieval tool and mutation tool must independently enforce:
- authenticated user ownership
- selected series scope
- persisted watch progress
- visible_from_order filtering
- allowed labels
- allowed relationship types
- bounded result counts
- bounded traversal depth
- fail-closed behavior

SECURITY MODEL

Treat the LLM as an untrusted planner.

The backend is the policy enforcement point.

The LLM:
- proposes tool calls
- receives already filtered tool results
- writes an answer
- may propose a structured ChangeSet

The backend:
- selects the authenticated user
- resolves current series progress
- applies spoiler filtering
- validates all tool parameters
- executes parameterized Cypher
- validates all mutations
- requires confirmation
- applies changes transactionally
- records revisions and audit metadata

==================================================
1. AUTHORITATIVE USER WATCH PROGRESS
==================================================

The LLM's visibility boundary must be derived from persisted backend state.

Do not trust:

visible_until_order supplied directly by the frontend.

Introduce or use an existing user-series progress model.

Suggested conceptual model:

(:User)-[:HAS_PROGRESS]->(:UserSeriesProgress)-[:FOR_SERIES]->(:Series)

UserSeriesProgress:
- id
- user_id
- series_id
- visible_until_order
- updated_at

A relational or different representation is acceptable only if already used by
the repository.

Required behavior:
- progress belongs to one authenticated user and one series
- progress update preserves the existing confirmation-modal UX
- frontend may request a progress change
- backend validates and persists it
- every GraphRAG request resolves progress server-side
- every retrieval tool receives the resolved boundary internally
- the LLM cannot choose or increase the boundary
- session owners cannot access another user's progress
- invalid or missing progress fails safely
- the current ordinary graph endpoint and chat retrieval must use compatible
  visibility semantics

Do not break existing episode selection.

2. CHAT AND MESSAGE PERSISTENCE
==================================================

Implement persistent per-user chat sessions.

Suggested models:

ChatSession:
- id
- user_id
- series_id
- title
- created_at
- updated_at
- deleted_at if soft deletion matches repository conventions

ChatMessage:
- id
- session_id
- role: user | assistant
- content
- created_at
- visible_until_order_snapshot
- status
- citations
- graph_focus
- change_set_id where applicable

Each assistant message must record the exact visible_until_order used to
generate it.

Critical regression scenario:

A user may:
1. progress to Episode 3
2. ask a question
3. receive Episode 3 information
4. move progress back to Episode 1
5. reopen the old chat

The old Episode 3 response must not leak through chat history.

Required behavior:
- messages generated at a boundary greater than the user's current boundary
  must not be returned
- hidden messages must not contribute to LLM conversation memory
- hidden messages must not appear in session previews
- session titles must not leak hidden content
- citations and ChangeSets above the current boundary must also be hidden
- API counts must not reveal the number of hidden messages
- moving progress upward may reveal eligible messages again
- moving progress downward must immediately hide unsafe messages
- do not delete hidden messages merely because progress decreased

Every request must verify:
- authenticated ownership
- matching series
- current progress
- message visibility

3. BACKEND CHAT API
==================================================

Use stable, explicit, series-scoped REST contracts.

A suitable route family is:

POST /api/series/{series_id}/chat/sessions
GET /api/series/{series_id}/chat/sessions
GET /api/series/{series_id}/chat/sessions/{session_id}
DELETE /api/series/{series_id}/chat/sessions/{session_id}

POST /api/series/{series_id}/chat/sessions/{session_id}/messages
POST /api/series/{series_id}/chat/sessions/{session_id}/messages/stream

Adapt route names to current conventions if necessary, but keep them consistent.

Requirements:
- explicit Pydantic request and response schemas
- authenticated user dependency
- ownership validation
- generic 404 behavior for inaccessible sessions
- consistent existing error envelope
- useful OpenAPI summaries and examples
- no Neo4j records in public responses
- no raw LLM provider objects in public responses
- bounded message length
- bounded history length
- bounded concurrent generations
- cancellation/disconnect handling where practical

Streaming:
- prefer server-sent events or a fetch-compatible streaming response
- stream answer text incrementally
- finish with a structured final event containing:
  - message ID
  - citations
  - graph focus
  - proposed ChangeSet
- do not expose private chain-of-thought
- do not expose raw tool reasoning
- do not expose model provider diagnostics

A non-streaming endpoint may remain for tests and fallback behavior.

5. get_timeline

- end visible order
- limit

6. get_claims
Inputs:

- limit

7. get_evidence
Inputs:
- claim IDs

8. get_sources
Inputs:

- limit

Inputs:

10. get_user_notes
Inputs:

Exact tool names may change, but responsibilities must remain explicit.

Tool rules:
- every query is parameterized
- series scope is mandatory
- visible_until_order comes from backend progress, not model input
- story-sensitive nodes require:
  visible_from_order IS NOT NULL
  AND visible_from_order <= resolved_visible_until_order
- story-sensitive relationships must also be visibility-filtered
- Claim, EvidenceFragment and Source visibility must be enforced
- hidden endpoint targets must behave like nonexistent resources
- cross-series references must be rejected
- traversal depth must be bounded
- result count must be bounded
- query timeouts should be considered
- no unrestricted label or relationship interpolation
- labels and predicates must come from server allowlists
- no user-provided raw Cypher fragments
- no model-provided raw Cypher fragments

Do not leak hidden information through:
- node counts
- path existence
- error messages
- search suggestions
- relationship counts
- timing-dependent alternate messages
- autocomplete
- citation metadata
- session titles

==================================================
6. RETRIEVAL AND CONTEXT-BUILDING PIPELINE
==================================================

Implement a deterministic GraphRAG-lite pipeline:

User message
→ input validation
→ current-user resolution
→ persisted-progress resolution
→ intent and entity planning
→ allowlisted retrieval tools
→ spoiler-filtered results
→ context normalization
→ LLM answer generation
→ citation validation
→ graph-focus extraction
→ response streaming

The model may decide which allowlisted retrieval tools to call, but it may not
write Cypher.

Limit tool rounds.

Prevent recursive or runaway tool calls.

Context builder must:
- deduplicate entities
- deduplicate claims and evidence
- prioritize direct evidence
- preserve stable IDs
- preserve source locators
- include visible order where useful internally
- omit User, Session, ChatSession and authentication data
- omit hidden graph data
- omit irrelevant properties
- stay within configured size limits
- rank direct matches over distant neighbors
- prefer verified/canonical claims while clearly retaining origin metadata
- treat candidate/user claims according to current domain semantics
- distinguish evidence from model inference

Context should have a clear structured format such as:

Series context
Current watched boundary
Relevant entities
Relevant relationships
Claims
Evidence fragments
Sources
User notes

Do not place secrets or PII in model context.

==================================================
9. SAFE GRAPH-EDITING AGENT
==================================================

The assistant must support graph modification, but only through structured tools.

The LLM must not directly execute writes.

Use a two-stage flow:

Stage 1 — Propose
- model constructs a typed ChangeSet
- backend validates it
- frontend displays a readable diff
- no database mutation occurs

Stage 2 — Confirm and apply
- authenticated user explicitly confirms
- backend revalidates against current graph and current progress
- backend applies the complete ChangeSet in one transaction
- revision/audit metadata is recorded
- frontend refreshes affected graph data

Suggested ChangeSet model:

ChangeSet:
- id
- user_id
- series_id
- chat_session_id
- status:
  draft | awaiting_confirmation | applied | rejected | failed | reverted
- visible_until_order_snapshot
- summary
- operations
- created_at
- confirmed_at
- applied_at
- revision_id
- idempotency_key

Suggested operation types:

- create_node
- update_node
- delete_node
- create_relationship
- update_relationship
- delete_relationship
- create_claim
- update_claim
- delete_claim
- attach_evidence
- create_note
- update_note
- delete_note

Adapt to existing domain APIs and ontology.

Each operation must use an explicit Pydantic discriminated union.

Example conceptual operation:

{
  "operation": "create_relationship",
  "source_id": "character:dexter",
  "target_id": "character:batista",
  "relationship_type": "WORKS_WITH",
  "properties": {
    "description": "..."
  },
  "selected_episode_order": 2
}

Do not accept:
- arbitrary labels
- arbitrary relationship types
- arbitrary properties
- raw Cypher
- hidden IDs
- cross-series IDs
- model-generated database IDs
- visible_from_order chosen freely by the model

The server must:
- generate stable IDs
- validate ontology labels
- validate relationship predicates
- validate property schemas
- ensure targets belong to the selected series
- ensure targets are currently visible
- derive visible_from_order server-side
- ensure derived visibility is not above current progress
- assign origin:user to new resources
- set creator user ID where appropriate
- validate all operations before applying any
- apply all operations transactionally
- roll back the entire ChangeSet on failure
- prevent replay with an idempotency key
- use optimistic conflict detection where appropriate
- preserve referential integrity
- reject orphaning Claims/Evidence where prohibited

11. DESTRUCTIVE ACTIONS AND CONFIRMATION
==================================================

Require explicit user confirmation for:
- delete node
- delete relationship
- delete claim
- delete evidence
- multi-operation ChangeSets
- changes affecting more than one graph element
- operations that may detach dependent user content

The chat message itself is not confirmation.

The frontend must present:
- human-readable summary
- each operation
- before values
- proposed after values
- affected graph elements
- visibility/episode placement
- warnings
- Confirm
- Reject

After confirmation, the backend must re-read:
- current user
- current progress
- current resource origin
- current resource version
- current series ownership

A ChangeSet created under a later watched boundary must not remain applicable
after the user lowers progress below its snapshot.

A stale or unsafe ChangeSet must become non-applicable and require regeneration.
