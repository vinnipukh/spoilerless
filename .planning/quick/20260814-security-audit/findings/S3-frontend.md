# S3 — Hostile Frontend Security Audit: hdgrafcehennemi / Spoilerless (React 19 + Vite + Cytoscape)

Audit date: 2026-08-14/15 · Auditor: subagent S3 (frontend) · Method: static analysis only; no live API calls; no `.env` values read (key names only). Scope: `frontend/` (React 19, Vite 8, TypeScript, Tailwind 4, Cytoscape.js, shadcn/radix), plus the frontend-facing parts of `spoilerless/app` needed to ground browser-security claims (headers, cookies, CORS).

Assumption of hostility: every frontend control is bypassable; enforcement lives (or must live) server-side. Findings below quote real code.

---

The shell therefore ships with **no CSP, no `frame-ancestors`/XFO, no `X-Content-Type-Options`, no Permissions-Policy, no HSTS** on the document that executes all app code. | Any XSS anywhere (future markdown rendering, compromised dependency, hostile LLM output if ever rendered as HTML) executes unrestricted: no `script-src` barrier, no `object-src 'none'`, no `base-uri 'self'`. No CSP header, no CSP meta. | Mirror the backend header set in `vercel.json` (`headers` per route) or add a CSP `<meta>` (mirror `main.py:48-54`, plus `frame-ancestors 'none'`): `default-src 'self'; script-src 'self' https://accounts.google.com; img-src 'self' data: https:; style-src 'self' 'unsafe-inline'; font-src 'self'; connect-src 'self' https://accounts.google.com; frame-src https://accounts.google.com; object-src 'none'; base-uri 'self'; form-action 'self'` + `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`. | Verified by reading `vercel.json`, `index.html`, `dist/index.html`, and `main.py` mount points.

## SEC-FE-002 | BYOK LLM API key stored plaintext in localStorage and transmitted to the app backend on every chat request | Medium (High impact; requires an XSS/extension to weaponize) | High | frontend/src/lib/byok.ts:9,60,71-85; frontend/src/api/chat.ts:41,87; frontend/src/components/settings/SettingsPage.tsx:99-107,166-168 | Browser Settings → "Save settings" / any chat request | `SettingsPage.handleSave` → `saveLLMSettings()` → `localStorage['spoilerless:byok-llm-settings']` (JSON incl. `api_key`) → `getLLMHeaders()` → `X-LLM-Api-Key` header on `POST /api/.../messages` and `/messages/stream` → Spoilerless backend → LLM provider | The user's Gemini/OpenAI-compatible API key is (a) readable by **any script executing in this origin** (localStorage is origin-wide — one XSS, one malicious dependency, or a browser extension turns into key theft; no `HttpOnly`-style protection exists for localStorage), and (b) sent to the Spoilerless backend (`api.spoilerless.net`) as a header on every chat call, i.e. it "leaves this browser" far more than the SettingsPage copy claims: "Your API key never leaves this browser except as a per-request header sent to the endpoint you configure above" (SettingsPage.tsx:166-168) — it is sent to the *app's* endpoint first, which proxies it. ## SEC-FE-003 | No URL-scheme validation on DB-supplied URLs rendered into `<a href>` and `<img src>` (javascript: click-exec; protocol-relative fetch quirk) | Medium | Medium (data is curated today; hostile DB/backend or future user-content URLs change this) | frontend/src/components/detail/DetailPanel.tsx:100-107, 826-832; frontend/src/api/client.ts:54-58 (`apiUrl`); frontend/src/components/graph/graphElements.ts:89,115 | Node DetailPanel "Image source" link / graph node portrait | `GraphResponse.nodes[].image_source_url` / `image_url` (DB/API) → `href={node.image_source_url}` / `apiUrl(node.image_url)` → `<a target=_blank>` / Cytoscape `background-image: data(imageUrl)` | `image_source_url` is rendered directly into an anchor `href` with no scheme allowlist. A hostile value `javascript:alert(document.cookie)` executes on click with full origin privileges (the session cookie is HttpOnly, but the script can call authenticated APIs and read the BYOK key — chains with SEC-FE-002). `image_url` (Character portraits) flows into Cytoscape `background-image` — canvas-drawn, so no script execution there, but `apiUrl()` passes any non-`/`-leading URL through unchanged and mishandles protocol-relative URLs: `//evil.example/x.webp` starts with `/` so it becomes `${base}//evil.example/...` → in dev (`base=''`) the browser fetches `https://evil.example/x.webp` (external request, no allowlist, no-referrer only strips the Referer). Set `image_url = "//attacker/x.webp"` → observe request to attacker host. | Validate schemes (`https:` only) for every URL sourced from the API before rendering into `href`/`src`; reject `javascript:`, `data:` (in href), and protocol-relative forms in `apiUrl()`; keep `rel="noopener noreferrer"` (already present, good). | Read `DetailPanel.tsx`, `client.ts:54-58`, `graphElements.ts:86-115`, `graphStylesheet.ts:119-126`.

## SEC-FE-005 | Cookie-auth surface: `credentials: 'include'` + no frontend CSRF token; all CSRF defense delegated to backend config (SameSite=Lax, Origin/Referer validation, CORS allowlist) | Medium | Medium | frontend/src/api/client.ts:60-70; frontend/src/api/chat.ts:83-92; spoilerless/app/api/deps.py:157-193; spoilerless/app/main.py:198-214; spoilerless/app/api/auth.py:69-78 | Any authenticated fetch | Browser fetch with cookies → `POST/PUT/DELETE /api/*` | Every state-changing call relies solely on the session cookie (`credentials: 'include'`, `client.ts:69`) — the frontend sends **no CSRF token**. Nothing in the frontend can detect or mitigate any of these. | Static: grep `allow_credentials` / `session_cookie_secure` / `samesite` (verified values above). | (S2/backend) keep `allow_credentials=True` only with a strict, env-validated origin allowlist; force `Secure` in prod; consider `SameSite=Strict` for a same-site custom-domain layout. Key conclusions for the consolidated report:
1. **The single highest-value fix is CSP + security headers on the Vercel-served shell** (SEC-FE-001) — it backstops every other finding (BYOK theft, supply chain, future XSS).
2. **BYOK key handling** (SEC-FE-002) is the most sensitive data the frontend touches; it is one XSS away from exfiltration.
3. **No exploitable XSS was found** in the current codebase — React-text/canvas rendering discipline is excellent (SEC-FE-010); the risk is forward-looking.
4. **Visitor/spoiler gating is purely cosmetic** (SEC-FE-006) — backend 401 enforcement is the actual control; S2 should verify each listed endpoint.
5. **CSRF posture is backend-only** (SEC-FE-005) — correct today, but single-layer config; flag for S2 (CORS allowlist, Secure flag, SameSite).
