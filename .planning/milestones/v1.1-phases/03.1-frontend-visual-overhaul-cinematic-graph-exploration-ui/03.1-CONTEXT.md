# Phase 03.1: Frontend Visual Overhaul (Cinematic Graph Exploration UI) - Context

**Gathered:** 2026-07-30
**Status:** Ready for planning
**Source:** User-authored phase brief pasted directly into `/gsd-plan-phase 03.1 --auto` (no discuss-phase run — brief is exhaustive enough to serve as locked context directly). Inserted as urgent decimal phase after Phase 3 via `/gsd-phase --insert 3` (see Roadmap Evolution in STATE.md).

<domain>
## Phase Boundary

Turn the existing functional Cytoscape graph interface into a premium, cinematic, high-contrast graph exploration product. The graph is the hero of the application. Frontend-only (`frontend/`) — no backend, API contract, Neo4j query, GraphRAG, FalkorDB, auth-architecture, spoiler-filtering, or `visible_until_order` changes. This phase does not implement or plan Phase 3's Notes/Manual-Editing frontend (still separately pending) or Phase 4's Revision History UI — it only restyles/restructures the existing Phase 2 graph experience and its detail panel.

This phase is **not** one of the 30 canonical Prototype v0 requirements (no REQUIREMENTS.md ID) — it is an out-of-band product-quality initiative the user requested on `feature/graph-visual-overhaul`, analogous in kind to the earlier out-of-band character-images and Google Sign-In work already merged to this branch's base.

</domain>

<decisions>
## Implementation Decisions

### Scope fence (hard constraints)
- **D-01:** Frontend only. Do not touch `backend/`, API response shapes, Neo4j Cypher, spoiler filtering, or `visible_until_order` semantics.
- **D-02:** Do not implement GraphRAG or migrate to FalkorDB. Do not change Google Sign-In/HttpOnly-session auth architecture.
- **D-03:** Preserve all existing Character/Claim/Evidence interactions, series/episode selection, watch-progress confirmation modal, session restoration, logout, spoiler filtering (returning to an earlier episode still hides future Claims/Evidence).
- **D-04:** Do not translate or rewrite existing content unnecessarily. Do not replace Cytoscape.js or add an unnecessary second UI framework. TypeScript only, no `any`.
- **D-05:** Do not commit until implementation + verification (lint, typecheck, build, tests) are complete. (Applies to the execute-phase step that follows this plan, not to this planning step itself.)

### Claim/Evidence architecture (resolved via user Q&A during planning — see AskUserQuestion log)
- **D-06:** **Claims, Evidence, and Sources stay OUT of the Cytoscape canvas** — they remain `claims[]` / `evidence[]` / `sources[]` arrays consumed only by `DetailPanel`'s Claims/Evidence tabs, exactly as today. Do **not** synthesize client-side Cytoscape nodes/edges for them. User explicitly picked this ("Panel + edge only") over full node synthesis after being shown the real numbers: today's `nodes[]` = Character/Event/Location/Organization/Episode/Series only (20 nodes at S01E03: 9 char + 3 event + 4 location + 3 episode + 1 series); seed has 9 claims / 9 evidence / 3 sources, and node-synthesis would have ~doubled node count and added ~30 synthetic edges, a materially bigger and riskier surface than a restyle phase warrants.
- **D-07:** The brief's "Claim: diamond/magenta" and "EvidenceFragment: document/orange" visual language is therefore re-scoped from *graph node shapes* to: (a) **claim-backed edges** (edge.claim_id !== null) get a distinguishable relationship treatment (see D-14/edge system below — these edges already carry a real relation `type`, e.g. `SUPPORTED_BY`, not a generic "Claim" edge type, so magenta is not automatically correct here — the researcher/planner should map claim-backed edges by their actual `edgeType`, and separately use magenta/orange as the **card accent colors** inside `DetailPanel`'s Claims tab and Evidence tab respectively), and (b) the DetailPanel Claims/Evidence tab cards themselves (magenta-accented claim cards, orange-accented evidence/source cards).
- **D-08:** `ontology/node_types.yaml` declares `Claim`, `Source`, `EvidenceFragment` as real Neo4j "knowledge" node types — this is a data-layer fact, not something to invent. D-06 only concerns whether the **frontend** additionally renders them as Cytoscape elements; it does not contradict "do not invent unsupported ontology types" since choosing not to render an already-real type is not inventing one.

### Real data model (ground truth — supersedes the brief's directional suggestions where they conflict)
- **D-09:** Actual current Cytoscape `nodeType` values (from `graphElements.ts` + `graphStylesheet.ts`): `Character`, `Event`, `Location`, `Organization`, `Episode`, `Series`, and `UserNote` (reserved for Phase 3, no seed data yet, dashed border already styled). `Object` is a declared ontology node type with **zero current seed instances** — style it defensively (falls into the "Unknown/default: muted slate" bucket) but do not build seed data for it.
- **D-10:** Actual relationship types (`ontology/relation_types.yaml`, authoritative — the brief's suggested taxonomy (`RELATED_TO`, `PARENT_OF`, `SIBLING_OF`, `ALLY_OF`, `FRIEND_OF`, `ENEMY_OF`, `CONFLICTS_WITH`, `ASSOCIATED_WITH`, `SOURCED_FROM`) **do not exist in this repo and must not be invented**. Real types, by ontology group:
  - `structural`: `PART_OF`, `PRECEDES`, `OCCURRED_IN`, `LOCATED_IN`
  - `participation`: `PARTICIPATED_IN`, `WITNESSED`, `CAUSED`, `AFFECTED`, `TARGETED`, `MENTIONED`
  - `character`: `KNOWS`, `FAMILY_OF`, `WORKS_WITH`, `TRUSTS`, `DISTRUSTS`, `HELPS`, `OPPOSES`, `THREATENS`, `ATTACKS`, `KILLS`
  - `provenance`: `SUPPORTED_BY`, `CONTRADICTED_BY`, `DERIVED_FROM`, `REFERS_TO`
  - `revision`: `CORRECTS`, `SUPERSEDES`, `REVERTS_TO` (Phase 4 territory — no current seed edges use these; map defensively, don't build demo data)
  - Researcher must additionally confirm which of these actually appear in `data/dexter/seed/claims.json`/`events.json` edges vs. which are ontology-declared-but-unused, and report exact counts.
- **D-11:** `GraphNode`/`GraphEdge`/`GraphClaim`/`GraphSource`/`GraphEvidence`/`GraphResponse` types in `frontend/src/types/graph.ts` are exact backend mirrors — do not change their shape. Only add new *derived/presentational* types (e.g. a node-style-mapping lookup type) alongside, never mutate the API-mirroring types.
- **D-12:** Existing selection model: `GraphCanvas.tsx` already implements tap-driven neighborhood highlight/fade via `selected-dominant` / `faded` / `hovered` / `edge-active` CSS classes and a centralized `App.tsx` branch that routes claim-backed edges to `DetailPanel` and structural edges (`claim_id === null`) to `StructuralEdgeCard`. Preserve this branch/contract — extend its visuals, don't replace its architecture.

### Design tokens & typography
- **D-13:** Replace `@fontsource-variable/geist` with `@fontsource-variable/space-grotesk` (headings/prominent controls) + `@fontsource-variable/inter` (body/UI/graph labels), following the exact same local-import pattern already used for Geist in `frontend/src/index.css` (`@import "@fontsource-variable/<name>"` + `--font-*` in the `@theme inline` block). Strong system-font fallback stacks required. No runtime Google Fonts.
- **D-14:** Build the color/token layer as CSS custom properties, extending the *existing* `:root`/`.dark` token block in `frontend/src/index.css` (already dark-first, already has `--background #0F172A`, `--card #192134`, `--accent #7C3AED`, `--secondary #6366F1`, `--muted-foreground #94A3B8`, etc., locked by the Phase 2 UI-SPEC) rather than starting a parallel token system. The brief's directional values (`#0B1020` app bg, `#111827` elevated surface, `#151C2E` panel surface, `rgba(148,163,184,0.14)` border, `#F8FAFC`/`#94A3B8` text, violet primary/cyan secondary accents) are **directional inputs to reconcile with the current locked palette**, not a mandate to discard it — the UI-SPEC gate (gsd-ui-phase → ui-ux-pro-max) produces the final cohesive palette; it should stay a close cousin of the current `#0F172A`/`#192134`/`#7C3AED`/`#6366F1` system rather than a wholesale swap, since Phase 2's palette is a locked prior decision and swapping it wholesale isn't required to satisfy the brief's actual complaints (weak hierarchy, gray edges, small nodes) — a "deepen and extend" of the existing palette is preferred over a "replace" unless the UI-ux-pro-max audit finds a strong reason otherwise.
- **D-15:** A single central relationship-style mapping module (one file, e.g. `frontend/src/components/graph/relationshipStyles.ts` or similar) is required — do not scatter edge-type colors across component files. Same principle for node-type styling: extend the existing single `graphStylesheet.ts`, don't fragment it.

### Application shell & episode navigation
- **D-16:** Preserve `AppShell.tsx`'s existing behavior contract exactly (series select → episode select → confirm modal → session restore → auth avatar/logout) while restyling. `EpisodeSelector.tsx` currently a bare shadcn `Select` — brief wants a segmented/pill control instead; must keep keyboard navigation and the existing `onSelect(episodeOrder)` contract intact, and must not change `ConfirmAdvanceModal`'s trigger conditions (fires on every progress change per Phase 2 D-03, forward or backward).
- **D-17:** Google avatar/logout block in `AppShell.tsx` (already implemented: avatar img with initials-icon fallback, ghost logout button) gets restyled only — behavior (calls existing `onLogout`/`useAuth`) is untouched.

### Graph canvas, layout, and background
- **D-18:** Current layout is `cose-bilkent` (`layoutOptionsFor`, `padding: 24`, `fit: true`, `nodeDimensionsIncludeLabels: true`), falling back to built-in `cose` only on an actual caught failure (module-scope `layoutName` variable) — this fallback mechanism must be preserved as-is. Per the brief: tune `cose-bilkent`'s own options (padding, node repulsion/spacing, `nodeDimensionsIncludeLabels`) and Cytoscape zoom constraints first; only add `fCoSE`/`cose-bilkent`-replacement dependencies if research shows tuning cannot fix the "tiny centered cluster in empty canvas" complaint, and justify the addition explicitly in RESEARCH.md before the planner locks it in.
- **D-19:** Current fixed `NODE_SIZE = 36` / `SERIES_NODE_SIZE = 46` in `graphStylesheet.ts` — confirmed root cause of "nodes too small." Must become type-aware sizing (larger baseline + per-type variance + modest selected-state growth), tuned together with layout spacing/padding and zoom min/max so labels stay readable and nodes don't overlap.
- **D-20:** No current zoom min/max, no background grid/glow — both must be added (`minZoom`/`maxZoom` on the Cytoscape instance, CSS-based subtle grid/dot texture + restrained radial glow behind the canvas container, not behind individual nodes). Must not use `background-image-crossorigin` on the canvas itself (see D-22) and must not degrade `cy.layout()` performance.
- **D-21:** `useEffect` re-running `runLayout(cy)` keyed on `[graph]` (episode-boundary changes only) must be preserved — do not add layout reruns on node-selection or tab-change (brief explicitly calls this out as a regression risk). `elements` is already `useMemo`'d on `[graph]` (fixed in Phase 2 04 after a real cose-bilkent-thrashing bug) — preserve this memoization pattern for any new derived-data computations (style lookups, etc.).

### Node visual system & character portraits
- **D-22:** Character portrait handling: `node[nodeType="Character"][imageUrl]` background-image is deliberately **not** using `background-image-crossorigin` today, with a documented reason in `graphStylesheet.ts` (Fandom's CDN sends no CORS headers; requesting `'anonymous'` makes Cytoscape draw a broken-image glyph instead of falling back cleanly). Preserve this exact tradeoff/reasoning — do not add `crossorigin` handling to "fix" it. Cytoscape already falls back to flat `background-color` on 404/blocked images with no broken-image box; the brief's "clean fallback, no broken-image visual" requirement is **already satisfied** by current behavior — verify, don't reinvent.
- **D-23:** `imageUrl` data key is only ever set for `Character` nodes with a non-null `image_url` (`graphElements.ts`); other node types can never accidentally match the portrait selector. Preserve this invariant when adding new per-type visual rules.
- **D-24:** Node-type shape/color mapping — apply the brief's suggested shapes/color-families to the **real** type list (D-09): Character (circle/ellipse, portrait-aware, cyan/violet ring by state), Event (rounded-rectangle, green/teal), Episode (already `shape: 'tag'` — keep a compact tag/pill treatment, amber/yellow family, season/episode code visible), Location (rounded-rectangle/marker-like, cyan/blue), Organization (currently `diamond` — keep shape, red/coral family per the brief's "Organization: red/coral"), Series (currently `star`, keep), `UserNote` (kept dashed/reserved, no new visual investment beyond what Phase 2 already did), `Object`/unknown (muted slate default, still 4.5:1+ text-contrast accessible). No "Claim"/"EvidenceFragment" node shapes per D-06/D-07.
- **D-25:** Origin border treatment (`origin === 'canonical'` → solid border, else dashed) is a locked Phase 2 decision — preserve it; new node-type color fills must not remove the ability to see solid-vs-dashed border origin state.

### Selection, neighborhood, hover, edges
- **D-26:** Extend (don't replace) the existing `selected-dominant` / `faded` / `hovered` / `edge-active` class contract: selected node gets a clear ring + restrained glow (glow = CSS `box-shadow`/Cytoscape `shadow-*` properties used sparingly per the performance constraint below, not per-element continuous animation); connected edges brighten + thicken slightly; unrelated content dims to a low-but-nonzero opacity (already `0.25`/`0.15` for node/edge — brief's "dim rather than disappear" is already the current design, tune values don't invent a new mechanism).
- **D-27:** Hover must brighten a **hovered node's own connected edges** — today only edge-hover-on-the-edge-itself is wired (`cy.on('mouseover', 'edge', ...)`); node hover currently only sets a native `title` tooltip. Adding "hovering a node highlights its edges" is new behavior explicitly requested by the brief and must not open `DetailPanel` (hover ≠ selection; click remains the only selection trigger, unchanged).
- **D-28:** Edge color-by-relationship-type is new (today all edges are near-invisible `rgba(255,255,255,0.08)` regardless of type, confirmed root cause of "edges look white/gray"). Map the real relation-type groups (D-10) to color families per the brief's category intent (family/identity → violet, trust/positive (`TRUSTS`,`HELPS`) → green, conflict/negative (`DISTRUSTS`,`OPPOSES`,`THREATENS`,`ATTACKS`,`KILLS`) → red/coral, professional/social (`KNOWS`,`WORKS_WITH`) → cyan/blue, participation (`PARTICIPATED_IN`,`WITNESSED`,`CAUSED`,`AFFECTED`,`TARGETED`,`MENTIONED`) → teal, structural/location (`OCCURRED_IN`,`LOCATED_IN`) → amber, pure structural backbone (`PART_OF`,`PRECEDES`) → slate/neutral (these aren't really "relationships," they're narrative scaffolding), provenance (`SUPPORTED_BY`,`CONTRADICTED_BY`,`DERIVED_FROM`,`REFERS_TO`) → orange, revision (Phase 4, unused today) → muted slate default. Arrow color must always match line color (already same selector today, keep pattern). Do not use color alone — keep/extend label text as the secondary channel.
- **D-29:** Dashed edge lines are reserved for a genuine candidate/unverified data state if one exists in the claim/edge model (researcher to confirm whether `GraphClaim.status` or similar ever signals "candidate"/"unverified" today) — not to be used decoratively. If no such state exists in current data, do not add dashed edges; document that as a forward-compat note instead.

### Legend, controls, detail panel, responsive, a11y, performance
- **D-30:** Add a compact collapsible legend (node colors/types, edge color families) and zoom-in/zoom-out/fit/reset controls, keyboard-accessible with tooltips/`aria-label`s, positioned so they never cover graph content.
- **D-31:** `DetailPanel.tsx`'s current Overview tab literally renders `<p>Type: {selectedNode.type}</p>` / `<p>Label: {selectedNode.label}</p>` — confirmed the brief's "avoid raw Type/Label text" complaint. Restyle into structured metadata rows/cards while preserving every existing displayed field (predicate/claim_type/status/confidence for edges; type/label for nodes) — no field removal. Claims tab / Evidence tab restyle into cards per D-07; `StructuralEdgeCard.tsx` (tab-less minimal card for structural edges) gets the same visual polish pass but keeps its distinct tab-less identity (Phase 2 D-06) — do not merge it into the tabbed `DetailPanel`.
- **D-32:** No revision-history data exists yet (Phase 4 unbuilt) — do not invent revision/history UI content; the brief's "History/revision sections... do not invent revision data the API does not provide" is a hard no-op for this phase.
- **D-33:** Responsive degradation only (brief's own words: "do not perform an unrelated full mobile redesign, provide a practical responsive degradation") — desktop-primary graph + stable-width panel, medium-width panel narrowing + compact episode labels, narrow/mobile detail panel becomes a drawer/sheet (the existing `Sheet` component already supports different `side`/sizing — reuse it, don't add a new sheet/drawer primitive).
- **D-34:** Accessibility: preserve keyboard focus order, visible focus rings, 4.5:1+ text contrast, `aria-label`s on icon-only graph controls, proper tab semantics for Overview/Claims/Evidence (already using Radix `Tabs` under the hood via shadcn — Radix gives this for free, don't hand-roll), `prefers-reduced-motion` support (disable/shorten the new hover/selection transitions), decorative grid/glow background must be `aria-hidden`/non-focusable.
- **D-35:** Performance: do not recreate the Cytoscape instance per render (already guarded via `wiredCyRef`/`cyInstanceRef` — preserve), memoize any new style-generation/mapping functions, no continuous/looping CSS animations on graph elements, avoid heavy per-element `filter`/multi-layer `box-shadow` (fine on the *selected* node singular, not on every node), clean up any new `cy.on(...)` listeners the same way existing ones are (module-scope registration, ref-guarded re-wiring).

### Claude's Discretion
- Exact final color values (the brief's hex values are explicitly "directional... not a requirement to use these exact colors" — the UI-SPEC/ui-ux-pro-max pass produces the locked final palette).
- Whether `fCoSE` replaces `cose-bilkent` — left to research findings + justification (D-18), default bias is "tune, don't replace."
- Exact spacing scale values, exact panel width breakpoints, exact glow/grid CSS implementation technique.
- Whether any additional Fontsource weight/subset beyond the two named packages is needed for the variable-font ranges actually used.
- Legend default open/collapsed state on first load.

<specifics>
## Specific Ideas

- "The graph itself is the hero of the application" — graph viewport utilization/fit/padding/zoom tuning is the single highest-priority visual change; a bigger, denser-feeling, less-empty canvas matters as much as color.
- Reference direction: "polished dark workspace... colorful graph entities... colorful relationship edges... sophisticated typography... clean episode controls... premium detail panel... subtle grid and glow... high graph readability... restrained animation... no generic dashboard appearance." Treat "restrained" as a hard constraint against decorative/continuous motion, not just a style preference.
- User was shown the real Claim/Evidence node-vs-panel tradeoff (node counts, synthetic-edge count) and explicitly chose the smaller-surface "Panel + edge only" option — this was a deliberate scope call, not a simplification imposed unilaterally.
