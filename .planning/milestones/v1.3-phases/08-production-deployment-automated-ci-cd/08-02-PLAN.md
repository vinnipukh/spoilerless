<objective>
Replace the single shared server-side LLM key with a per-request,
browser-held bring-your-own-key flow (backend passthrough architecture per
D-04): the frontend collects and stores the key/base_url/model in
`localStorage` only, sends them as headers on every chat request, and the
backend constructs the LLM provider from those headers first, falling back to
the existing server-side settings only when no header key is present. This
directly closes the shared-key SSRF/theft surface docs/PROBLEMS.md #5
describes (an attacker can now only ever redirect their own key to their own
chosen host, never another user's).

Purpose: Zero LLM cost to the operator, key never persisted server-side,
existing spoiler-safe tool-calling loop stays entirely on the backend
(D-04 — chosen over full client-side LLM calls).
Output: Working per-user BYOK chat; server env/stored settings become an
optional fallback only.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser localStorage <-> chat request headers | User-controlled secret leaves the browser only as a per-request header to the backend the user already trusts |
| Backend request memory <-> external LLM provider | The BYOK base_url is user-supplied and could point anywhere reachable from Render |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-02-01 | Information Disclosure | BYOK key exfiltration via attacker-controlled base_url (docs/PROBLEMS.md #5) | high | mitigate | Per-request, never-persisted key construction (D-04..D-08); residual risk shrinks from "any user redirects the shared operator key" to "a user can only ever exfiltrate their own key to their own chosen host" |
| T-08-02-02 | Information Disclosure | BYOK key accidentally logged by request-logging middleware | high | mitigate | get_llm_provider never assigns the header value to a log-reachable variable in this plan; the Ops plan's request-logging middleware explicitly redacts X-LLM-Api-Key by name |
| T-08-02-03 | Tampering | Malformed/malicious base_url scheme (file://, gopher://) | medium | mitigate | Reuses LLMSettingsUpdate._validate_base_url's http/https-only, host-required check on the header value |
| T-08-02-04 | Repudiation | No record of which provider a chat turn used, since the key is never stored | low | accept | Acceptable for this milestone — BYOK is inherently client-attributed; no server-side audit trail requirement exists in AI-01..03 |

</threat_model>
