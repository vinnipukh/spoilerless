## Summary

This phase is a pure visual/UX overhaul of an already-functional, already-tested React 19 + Cytoscape.js 3.34 + Tailwind v4/shadcn product. The plan should treat this as "extend in place," not "rebuild": every architectural seam (module-scope layout registration + ref-guarded re-wiring, `useMemo`-on-`[graph]` element mapping, the centralized `App.tsx` branch that routes claim-backed vs. structural edges to two different detail components, the single `graphStylesheet.ts` and future single `relationshipStyles.ts`) is already correct and battle-tested (it fixed a real cose-bilkent layout-thrashing bug in Phase 2 Plan 04) — the job is to widen these seams with new tokens, new type-aware sizing, new edge-color mapping, new hover behavior, and a restructured (not re-architected) DetailPanel, while leaving six passing Vitest test files' underlying assertions intact or deliberately, visibly updated in the same task.

The single highest-leverage, lowest-risk change is graph-canvas tuning: the current `NODE_SIZE = 36`, default `cose-bilkent` `padding: 24`/`idealEdgeLength: 50`/`nodeRepulsion: 4500`, and the total absence of `minZoom`/`maxZoom` are jointly responsible for the "tiny centered cluster in empty canvas" complaint. This is genuinely fixable by tuning `cose-bilkent`'s own options (this research recommends specific numbers below) plus real node-size increases plus zoom bounds — the actual graph topology (20 nodes / up to 16 edges at full unlock, only 11 nodes / 6 edges at S01E01) is small enough that `cytoscape-fcose`'s advantages (constraint-based placement, better scaling to hundreds/thousands of nodes) are not needed. **Recommendation: tune, do not add a new layout dependency.**

A second, previously-unconfirmed finding materially changes one of CONTEXT.md's open questions: `GraphClaim.status === 'candidate'` DOES exist in the current real Dexter seed data (one claim, `dexter:claim:s01e01:temporary_trust`, `TRUSTS` predicate, `confidence_level: medium`, expires at `valid_until_order: 1`) — this is a genuine, real, non-hypothetical "candidate/unverified" data state, distinct from `origin` (which is 100% `"canonical"` across all current seed data — `origin=candidate`/`origin=user` do not appear anywhere yet). D-29's dashed-edge treatment therefore has a real, if narrow (1 of 9 claims, visible only at the S01E01 boundary), justification if the planner chooses to build it — see `## Ground-Truth Data Findings`.

A third finding corrects an assumption embedded in D-26's phrasing: Cytoscape.js core has **no** `shadow-*` style property, and CSS `box-shadow` cannot target a canvas-rendered node (Cytoscape draws to `<canvas>`, not per-node DOM elements). The correct native mechanism for a "restrained glow" on the selected node is Cytoscape's own `overlay-color`/`overlay-opacity`/`overlay-padding` style properties (a soft halo behind the element, GPU/canvas-rendered, cheap). CSS `box-shadow`/gradient glow remains valid ONLY for the background-grid/glow behind the whole canvas *container* `<div>` (D-20), which is a real DOM element.

**Primary recommendation:** Tune `cose-bilkent` in place (bigger `idealEdgeLength`/`nodeRepulsion`/`padding`, add `minZoom`/`maxZoom`), triple down on type-aware node sizing, build one new `relationshipStyles.ts` module mapping the 9 relation types that actually appear on canvas edges today to 6 color families (not 8 — 2 of the requested 8 families can only ever appear in `DetailPanel`, never on canvas edges, per the Ground-Truth findings below), restructure `DetailPanel`'s Overview tab into label/value rows while explicitly updating the 2 test assertions that currently depend on its exact literal text shape, and reconcile the token palette by adding four new tokens (`--canvas-surface`, `--panel-surface`, `--elevated-surface`, `--glow-accent`) alongside the existing locked Phase 2 token block rather than replacing any of it.

Verified by reading `backend/app/spoiler/filter.py` (`STRUCTURAL_EDGES_QUERY`, `VISIBLE_CLAIMS_QUERY`, `VISIBLE_USER_RELATIONSHIPS_QUERY`) and `backend/app/services/graph.py` (`fetch_graph`, which builds `GraphResponse.edges` from exactly three sources) plus the real seed JSON (`data/dexter/seed/claims.json`, `events.json`):

| Source of edge | Relation types that can appear | Verified count in current seed (full S01E03 unlock) |
|---|---|---|
| `STRUCTURAL_EDGES_QUERY` (`MATCH ... -[edge:PART_OF\|PRECEDES\|OCCURRED_IN]->`) | `PART_OF`, `PRECEDES`, `OCCURRED_IN` **only** — `LOCATED_IN` is declared in the ontology's `structural` group but is never queried/never created anywhere in `backend/app/graph/seed.py` | `PART_OF`: 3 (episode→series), `PRECEDES`: 2 (episode chain), `OCCURRED_IN`: 3 (event→location) = **8** |
| `VISIBLE_CLAIMS_QUERY` → `GraphService.fetch_graph`'s `projected_edges` (`edge.type = claim.predicate`) | Whatever predicate value appears on a `Claim` record — in current seed: `FAMILY_OF`, `WORKS_WITH`, `DISTRUSTS`, `TRUSTS`, `KNOWS`, `PARTICIPATED_IN` | At S01E03 boundary: `FAMILY_OF`×3, `WORKS_WITH`×2, `DISTRUSTS`×1, `KNOWS`×1, `PARTICIPATED_IN`×1 = **8** (the 9th claim, `TRUSTS`/`temporary_trust`, expires at `valid_until_order:1` and is invisible from S01E02 onward) |
| `VISIBLE_USER_RELATIONSHIPS_QUERY` (Phase 3 `UserNote`/user-authored relationships) | Restricted to `ontology.user_safe_relationship_types` = participation ∪ character groups | **Zero rows today** — no `origin='user'` claims exist in seed data yet (Phase 3 backend-only slice, no seeded user content) |

**Types that are ontology-declared but structurally CANNOT appear on a canvas edge today, and in most cases never can (not just "unused" but architecturally excluded):**
- `LOCATED_IN` — never queried by the structural-edges Cypher; declared-but-dead code path.
- `WITNESSED`, `CAUSED`, `AFFECTED`, `TARGETED`, `MENTIONED` (participation, beyond `PARTICIPATED_IN`), `HELPS`, `OPPOSES`, `THREATENS`, `ATTACKS`, `KILLS` (character, beyond the 4 present) — no current claim uses these predicates. These COULD appear on a future claim-projected edge if seed data is extended (they are not structurally excluded, just unused today).
- `SUPPORTED_BY`, `CONTRADICTED_BY`, `DERIVED_FROM`, `REFERS_TO` (provenance) — **these are structurally excluded from ever appearing as a `GraphEdge.type` on the canvas.** `SUPPORTED_BY`/`REFERS_TO` exist as real Neo4j relationships, but only between `Claim`→`EvidenceFragment`/`Source` nodes, which are never included in `VISIBLE_NODE_LABELS` (`backend/app/api/graph.py`) and never selected by any of the three edge-producing queries above. This confirms and strengthens D-07's instinct: the brief's "provenance → orange" edge-color mapping is **dead code on the graph canvas** as currently architected. It only matters for `DetailPanel`'s Evidence/Claims tab card accents (D-07b), never for a Cytoscape stylesheet selector. The planner should not spend implementation effort wiring an on-canvas selector for these four types beyond one small defensive fallback rule (see `relationshipStyles.ts` recommendation below).
- `CORRECTS`, `SUPERSEDES`, `REVERTS_TO` (revision) — Phase 4 territory, genuinely zero current or near-term seed data; map defensively only.

**Net effect for the planner:** the real, must-work-correctly edge-color mapping surface is **9 relation types** (`PART_OF`, `PRECEDES`, `OCCURRED_IN`, `FAMILY_OF`, `WORKS_WITH`, `DISTRUSTS`, `TRUSTS`, `KNOWS`, `PARTICIPATED_IN`), not the full ontology's 27. Everything else needs only a single generic defensive fallback selector (any `edgeType` not in the known map falls back to `--edge-slate`/muted, per D-28's "revision → muted slate default" precedent generalized to all未-mapped types) — this keeps `relationshipStyles.ts` small and testable, and correctly documents the other 18 as forward-compatible/future scope rather than building unreachable code paths.

### `GraphClaim.status` — a real "candidate" state exists (answers D-29 definitively: YES)

Verified by reading `data/dexter/seed/claims.json` directly:

```json
{"id":"dexter:claim:s01e01:temporary_trust", ...,
 "predicate":"TRUSTS", "claim_type":"inferred_state",
 "status":"candidate", "confidence_level":"medium",
 "relationship_effect":0.2, "visible_from_order":1,
 "valid_from_order":1, "valid_until_order":1, ...}
```

This is `status: "candidate"` (from `ontology/claim_types.yaml`'s `claim_statuses` enum: `candidate`/`corroborated`/`canonical`/`disputed`/`rejected`) — a real, live claim record, not a hypothetical. It is visible only when `visible_until_order === 1` (S01E01) because `valid_until_order: 1` excludes it from S01E02/S01E03 responses. Its `origin` field, however, is `"canonical"` (all 9 seed claims have `origin: "canonical"` — `origin: "candidate"`/`origin: "user"` literally do not exist anywhere in current seed data).

**This is an important distinction the plan must not conflate:**
- `origin` (governs D-25's existing solid/dashed **border** treatment) — 100% `"canonical"` today across all nodes/edges. The existing origin-based dashed-border mechanism will never fire for any current data (it is correctly forward-compatible for Phase 3/5, not currently exercised).
- `status` (a `GraphClaim`-only field, distinct from `origin`) — has a real `"candidate"` value on one claim today, exposed to the frontend as `claims[].status` (already rendered as plain text in `DetailPanel`'s Overview tab: `Status: {activeClaim.status}`).

**Consequence for D-29:** if the planner wants to honor the brief's "dashed = unverified" idea using this real field, it is a **new, small, additive feature** — reusing the existing `origin`-based dashed-border selector will NOT dash this edge (its `origin` is canonical). The correct implementation path is a new selector keyed on the claim's `status` (resolved via `edge.claimId` → `graph.claims[]` lookup, the same lookup pattern `DetailPanel.tsx`/`App.tsx` already use for claim resolution) — e.g. `edge[claimStatus = "candidate"]` after `graphElements.ts` (or a wrapper) is extended to compute and attach a derived `claimStatus` field per edge. This does not violate D-11 (which restricts the exported TypeScript *types*, not `ElementDefinition.data` presentational payloads). Given it affects exactly 1 of 9 current edges and only at one episode boundary, this research recommends treating it as a **Claude's-discretion nice-to-have**, not a blocking requirement — but it is no longer a "no-op, document as forward-compat" situation as D-29 anticipated; a genuine, real, correctly-scoped implementation is available if the planner wants it. The test fixture `frontend/src/test/fixtures/graphResponse.ts` already independently encodes an identical pattern (`claim_4`, `status: 'candidate'`, `valid_until_order: 1`) — this is not a one-off coincidence, it is the same intentional seed-data shape mirrored in test fixtures, reinforcing that this is a stable, real pattern to design for rather than an edge case to ignore.

## Layout Algorithm Decision (D-18)

**Recommendation: tune `cose-bilkent` in place. Do not add `cytoscape-fcose` or any other layout dependency this phase.**

**Current state (verified in `GraphCanvas.tsx`):**
```ts
function layoutOptionsFor(name: 'cose-bilkent' | 'cose') {
  return name === 'cose-bilkent'
    ? { name: 'cose-bilkent', nodeDimensionsIncludeLabels: true, fit: true, padding: 24 }
    : { name: 'cose', fit: true, padding: 24 }
}
```
Every other `cose-bilkent` option (verified from the installed package's own `README.md`) is left at its library default: `nodeRepulsion: 4500`, `idealEdgeLength: 50`, `edgeElasticity: 0.45`, `gravity: 0.25`, `gravityRange: 3.8`, `numIter: 2500`, `quality: 'default'`, `randomize: true`, `tile: true`.

**Why tuning is sufficient for this graph's actual topology:** at full S01E03 unlock the visible graph is 20 nodes / 16 edges (verified above); at S01E01 it is 11 nodes / 6 edges. `cytoscape-fcose`'s documented advantages over `cose-bilkent` are (a) constraint-based layout (relative/absolute node alignment, fixed positions) and (b) materially better performance/quality at hundreds-to-thousands of nodes. Neither advantage is reachable at 11–20 nodes — a correctly-tuned spring-embedder layout (which `cose-bilkent` already is) produces equivalent visual quality at this scale. The "tiny centered cluster in empty canvas" complaint is fully explained by three independently-fixable current settings, not by an algorithm-class limitation:
1. `NODE_SIZE = 36` is small in absolute pixels regardless of layout spread.
2. `idealEdgeLength: 50` (library default) pulls nodes close together, producing a physically small bounding box that `fit: true` then zooms in on — but with no `minZoom`/`maxZoom` floor/ceiling, a small bounding box at a *small* node count (e.g. 11 nodes at S01E01) can still end up looking sparse/empty because there simply isn't much graph to fill the canvas with, while a *denser* graph (20 nodes) with the same small `idealEdgeLength` ends up visually cramped instead. Both symptoms are two sides of the same root cause: no deliberate node-size/spacing/zoom-bound tuning has ever been done — the shipped values are 100% library/first-attempt defaults.
3. `padding: 24` is a small, fixed value that leaves a large empty margin ring at low node counts once `fit: true` zooms to include it.

**Concrete tuning recommendation** (values chosen conservatively relative to the library's documented ranges; must be visually verified during execution/UAT since no live rendering was available in this research session — flagged as `[ASSUMED]`, tag also applied inline below):
```ts
{
  name: 'cose-bilkent',
  quality: 'default',              // unchanged; 'proof' unnecessary at this node count
  nodeDimensionsIncludeLabels: true, // unchanged
  fit: true,                        // unchanged
  padding: 56,                      // was 24 — more breathing room framing the fitted graph
  nodeRepulsion: 7000,               // was 4500 (default) — moderately more spread
  idealEdgeLength: 90,               // was 50 (default) — longer edges, less clustering
  gravity: 0.2,                      // was 0.25 (default) — slightly looser pull to center
  numIter: 2500,                     // unchanged — plenty for <=20 nodes
  randomize: true,                   // unchanged
  tile: true,                        // unchanged
}
```
Combined with (declaratively, via `react-cytoscapejs`'s already-supported props — confirmed in `@types/react-cytoscapejs`): `minZoom={0.5}` and `maxZoom={2.25}` on the `CytoscapeComponent`, so neither a sparse 11-node graph nor a denser 20-node graph can auto-fit to an extreme zoom level. **[ASSUMED — exact numeric values need visual confirmation during implementation/UAT; the direction (increase padding/idealEdgeLength/nodeRepulsion, add zoom bounds) is HIGH confidence, the specific numbers are a reasonable starting point, not verified pixel-for-pixel since no dev server could be run in this sandboxed research session.]**

The existing try/catch fallback to built-in `cose` (module-scope `layoutName` variable) must be preserved exactly as today (D-18) — `layoutOptionsFor('cose')` should receive the same `padding`/`fit` bump for visual consistency in the (currently never-triggered) fallback path.

### Pattern 1: Central relationship-style mapping module (D-15)
**What:** One exported lookup (e.g. `getEdgeColor(edgeType: string): { line: string; label: string }`) consumed by `graphStylesheet.ts`'s edge selectors via a Cytoscape `mapData`/function-value style (Cytoscape supports style values as functions of element data), so the color logic lives in exactly one place and is independently unit-testable.
**When to use:** Any place an edge color is needed (canvas stylesheet, legend swatches) — the legend (D-30) and the stylesheet must read from the SAME module, not duplicate the color list, to avoid drift.
**Example:**
```ts
// relationshipStyles.ts — illustrative shape, not a source-verified snippet
export type EdgeColorFamily = 'violet' | 'green' | 'coral' | 'cyan' | 'teal' | 'amber' | 'slate'

const EDGE_TYPE_TO_FAMILY: Record<string, EdgeColorFamily> = {
  FAMILY_OF: 'violet',
  TRUSTS: 'green', HELPS: 'green',
  DISTRUSTS: 'coral', OPPOSES: 'coral', THREATENS: 'coral', ATTACKS: 'coral', KILLS: 'coral',
  KNOWS: 'cyan', WORKS_WITH: 'cyan',
  PARTICIPATED_IN: 'teal', WITNESSED: 'teal', CAUSED: 'teal', AFFECTED: 'teal', TARGETED: 'teal', MENTIONED: 'teal',
  OCCURRED_IN: 'amber', LOCATED_IN: 'amber',
  PART_OF: 'slate', PRECEDES: 'slate',
}
const FAMILY_HEX: Record<EdgeColorFamily, string> = {
  violet: '#8B5CF6', green: '#22C55E', coral: '#F43F5E', cyan: '#38BDF8',
  teal: '#2DD4BF', amber: '#FBBF24', slate: '#64748B',
}
const DEFAULT_HEX = 'rgba(148, 163, 184, 0.45)' // any unmapped/future type (provenance, revision, etc.)

export function edgeColorFor(edgeType: string): string {
  const family = EDGE_TYPE_TO_FAMILY[edgeType]
  return family ? FAMILY_HEX[family] : DEFAULT_HEX
}
```
This is illustrative — not copied from an external source (no verified upstream reference exists for this project-specific mapping); it directly encodes D-28's category intent reconciled against the Ground-Truth Data Findings above (9 real types, defensive default for the other 18).

### Pattern 2: Cytoscape function-style values for per-element color (avoids a huge stylesheet)
**What:** Cytoscape's `StylesheetJsonBlock.style` accepts a function `(ele) => value` for most properties, not only static values or `data(field)` strings. This lets `graphStylesheet.ts` call into `relationshipStyles.ts` directly:
```ts
{
  selector: 'edge',
  style: {
    'line-color': (ele: cytoscape.EdgeSingular) => edgeColorFor(ele.data('edgeType')),
    'target-arrow-color': (ele: cytoscape.EdgeSingular) => edgeColorFor(ele.data('edgeType')),
  },
},
```
**When to use:** Any per-element style that depends on a lookup table rather than a single `data(field)` passthrough — avoids writing one CSS-like selector per relation type (27 possible types would otherwise mean 27 selectors).

### Pattern 3 (existing, preserve): Selection-driven neighborhood highlight/fade
Already implemented in `GraphCanvas.tsx`'s `tap` handlers (`closedNeighborhood()`/`connectedNodes()`, `.faded`/`.selected-dominant`/`.edge-active` classes) and `graphStylesheet.ts`'s corresponding selectors — extend the existing selectors' property VALUES (bigger ring, restrained `overlay-*` glow) without touching the class-assignment logic in `GraphCanvas.tsx`'s tap handlers.

### Anti-Patterns to Avoid
- **CSS `box-shadow`/`filter: drop-shadow` on individual Cytoscape nodes:** does not work — nodes are canvas-rendered, not DOM elements. Use `overlay-color`/`overlay-opacity`/`overlay-padding` (native Cytoscape node/edge style properties, confirmed present in `@types/cytoscape`) instead for any per-node "glow."
- **Re-filtering by `visible_from_order` inside `graphElements.ts`:** explicitly forbidden by the file's own threat-model comment (T-02-03) — the backend has already applied spoiler filtering; do not add a second, redundant, drift-prone filter.
- **Scattering edge-type color literals across `graphStylesheet.ts`, `GraphLegend.tsx`, and `DetailPanel.tsx`:** violates D-15 — all three must import from the single `relationshipStyles.ts` module.
- **Layout reruns on selection/tab change:** the `useEffect` keyed on `[graph]` (not `[selectedElement]`) must not be widened — D-21 explicitly calls this out as a regression risk observed in Phase 2.

## Common Pitfalls

### Pitfall 1: Cytoscape has no `shadow-*` style property; CSS `box-shadow` cannot target a canvas-rendered node
**What goes wrong:** Implementing D-26's "restrained glow" literally as CSS `box-shadow` on a `.selected-dominant` class, or looking for a `shadow-blur`/`shadow-color` Cytoscape style property, will silently do nothing (no error, the node just never glows) — because Cytoscape.js draws all node/edge geometry to a single `<canvas>` element; there is no per-node DOM element for CSS to target, and no `@types/cytoscape` style property list entry named `shadow-*` exists.
**Why it happens:** D-26's own phrasing ("glow = CSS box-shadow/Cytoscape shadow-* properties") implies both are valid options; only one Cytoscape-native mechanism (`overlay-color`/`overlay-opacity`/`overlay-padding`) actually exists.
**How to avoid:** Use `overlay-color`, `overlay-opacity`, `overlay-padding` (confirmed present in `@types/cytoscape`'s style property definitions) on the `.selected-dominant`/`.hovered` node selectors. CSS `box-shadow`/gradient glow remains valid ONLY for the canvas *container* `<div>` background (D-20's grid/glow layer), which is a real DOM element sitting behind (not inside) the Cytoscape canvas.
**Warning signs:** A "selected glow" that never visibly appears in manual testing despite the CSS rule being present and the class being correctly applied — check whether the property name is a real Cytoscape style key before assuming a class/selector bug.

### Pitfall 2: Restructuring `DetailPanel`'s Overview tab will break 2 existing test assertions unless updated in the same task
**What goes wrong:** `DetailPanel.test.tsx` contains `expect(await screen.findByText('Type: Character')).toBeInTheDocument()` and `expect(await screen.findByText('Predicate: works_at')).toBeInTheDocument()` — these assert an exact literal text NODE reading `"Type: Character"` / `"Predicate: works_at"` as one contiguous string. D-31 requires restyling the raw `<p>Type: {type}</p>` into "structured metadata rows/cards" — if the new markup splits the label and value into separate elements (e.g. `<span>Type</span><span>Character</span>` with no literal `"Type: Character"` string anywhere in the DOM), these two `getByText` calls will fail even though the *data* is still displayed correctly.
**Why it happens:** `screen.findByText`/`getByText` matches against a single rendered text node by default; visually restructuring a label+value pair into separate DOM nodes changes what text node exists, even when the same information is present.
**How to avoid:** Either (a) preserve the literal `"Type: Character"`/`"Predicate: works_at"` string as one text node inside the new structured-row markup (e.g., a `<dt>Type</dt><dd>Character</dd>` pair CAN still be found via `getByText('Type: Character')` only if that exact string exists somewhere — safest is to keep rendering `{`${label}: ${value}`}` as one string inside a styled wrapper), or (b) deliberately update these 2 assertions in the SAME task that restructures the Overview tab (e.g., change to `screen.getByText('Character')` alongside a `screen.getByText('Type')` label check) — per D-31, the underlying field must still be displayed, but the exact literal string is not itself a locked contract (unlike, e.g., the Copywriting Contract's error/empty-state copy, which IS locked). Whichever approach is chosen, it must be an explicit, visible decision in the plan/task, not an accidental test break discovered only at verification time.
**Warning signs:** `npm run test` failing on `DetailPanel.test.tsx` after an Overview-tab restyle, with a "Unable to find an element with the text: Type: Character" error.

### Pitfall 3: `graphStylesheet.ts`'s `NODE_SIZE`/`SERIES_NODE_SIZE` module-level constants are currently the ONLY sizing mechanism — a type-aware sizing change touches every node selector, not just one constant
**What goes wrong:** The current code has exactly two size constants (`NODE_SIZE = 36`, `SERIES_NODE_SIZE = 46`) referenced by the base `node` selector and the `Series` selector respectively; every other type (Character, Event, Location, Organization, Episode, UserNote) currently inherits `NODE_SIZE` implicitly via CSS cascade (no explicit `width`/`height` override). Introducing per-type sizes requires adding explicit `width`/`height` to EVERY type selector that previously relied on the base fallback — a partial edit (e.g., only adding a Character override) will leave Event/Location/Organization/Episode still at the old `36px` base, silently defeating the "type-aware sizing" goal for those types.
**Why it happens:** The current stylesheet's node-type selectors (lines 44–93 of `graphStylesheet.ts`) only ever set `shape`, never `width`/`height`, except for `Series`.
**How to avoid:** Treat this as a full pass over every node-type selector in `graphStylesheet.ts`, not a single constant change; verify with a quick `grep -c "width:" graphStylesheet.ts` before/after to confirm every type got an explicit size.
**Warning signs:** After the change, some node types still visually appear at the old small size while others are bigger — a partial, inconsistent-looking result rather than a uniform improvement.

### Pitfall 4: The `imageUrl` background-image / `background-image-crossorigin` tradeoff is already correctly handled — do not "fix" it
**What goes wrong:** A well-intentioned attempt to add `crossorigin: 'anonymous'`/`background-image-crossorigin` handling to Character portraits, believing it will improve the "clean fallback" behavior — this actually makes things WORSE (Fandom's CDN sends no CORS headers, so requesting anonymous-mode CORS makes the browser treat the response as a load failure and Cytoscape draws its own broken-image glyph instead of the current clean flat-color fallback).
**Why it happens:** The brief's "clean fallback, no broken-image visual" requirement sounds like it needs new handling, but `graphStylesheet.ts`'s own inline comment already documents that the current no-crossorigin approach IS the clean-fallback behavior (confirmed correct by this research — Cytoscape falls back to the node's flat `background-color` on any image load failure when no `crossorigin` mode is set).
**How to avoid:** Verify this behavior is already correct (as this research does) rather than re-implementing it; D-22 explicitly calls this out as a "verify, don't reinvent" item.
**Warning signs:** None expected if this pitfall is heeded — included here because it's an easy, plausible-sounding "improvement" a plan/executor might reach for without checking the existing documented tradeoff first.

### Pitfall 5: `SelectedEdge`'s `edgeType` field is the raw wire value (e.g. `PART_OF`, `FAMILY_OF`) — legend swatches and edge-color lookups must use the SAME casing/string, not a human-readable transform
**What goes wrong:** If `GraphLegend.tsx` hardcodes a human-readable label list ("Family", "Trust", "Conflict"...) independently of `relationshipStyles.ts`'s actual `EDGE_TYPE_TO_FAMILY` keys, the legend can silently drift out of sync with the real edge-color map (e.g., a future seed-data addition of a new predicate would show on canvas with the correct color but never appear in the legend, or the legend could show a family that in fact maps to a different color than what's actually rendered).
**Why it happens:** Two independently-authored lists (stylesheet mapping + legend copy) for the same underlying data are a classic drift source, which is exactly why D-15 mandates a single central module.
**How to avoid:** `GraphLegend.tsx` must import its family list and color values from the same `relationshipStyles.ts` module that `graphStylesheet.ts` uses — never duplicate the mapping.
**Warning signs:** Legend and canvas showing different colors for what should be the same relationship type.
