## 1. Overview

HD Graf Cehennemi exposes a RESTful HTTP API backed by a Neo4j graph database. All data is **series-scoped** — every route that reads or writes story content requires a `series_id` path parameter.

The core architectural invariant is **spoiler-aware access**: every story-sensitive read requires a `visible_until_order` query parameter that represents how far the user has watched. The backend applies Cypher-level visibility filtering so the frontend never receives data it would need to hide.

**24 HTTP operations over 17 unique path templates** (including `/health`).

## 3. Authentication

Authentication is optional in development. When `GOOGLE_CLIENT_ID` is configured, Google Sign-In provides user identity via ID token verification.

### 3.1 POST /api/auth/google

Sign in with a Google ID token. Verifies the token signature, issuer, audience (`GOOGLE_CLIENT_ID`), and expiration. Creates or updates a local user record keyed on Google's `sub` claim. Sets an HttpOnly session cookie on success.

**Request body:**

```json
{
  "credential": "<Google ID token (JWT)>"
}
```

**200 response:**

```json
{
  "user": {
    "id": "user:abc123",
    "google_sub": "1234567890",
    "email": "user@example.com",
    "display_name": "Test User",
    "avatar_url": "https://lh3.googleusercontent.com/...",
    "created_at": "2026-01-01T00:00:00Z",
    "updated_at": "2026-01-01T00:00:00Z"
  }
}
```

**Errors:** `401 authentication_failed`, `401 auth_disabled`, `422 invalid_request`

### 3.2 GET /api/auth/me

Read the session cookie and return the currently authenticated user.

**200 response:**

```json
{
  "user": {
    "id": "user:abc123",
    "google_sub": "1234567890",
    "email": "user@example.com",
    "display_name": "Test User",
    "avatar_url": "https://lh3.googleusercontent.com/...",
    "created_at": "2026-01-01T00:00:00Z",
    "updated_at": "2026-01-01T00:00:00Z"
  }
}
```

**Errors:** `401 unauthenticated`

### 3.3 POST /api/auth/logout

Invalidate the server-side session and clear the cookie. Always returns 204 even if no valid session exists.

**Response:** `204 No Content` (no body)

```json
      "status": "canonical",
      "confidence_level": "verified",
      "relationship_effect": 1.0,

  "sources": [
    {
      "id": "source:dexter_s01",
      "label": "Dexter Season 1",
      "episode_id": "dexter:s01e01",
      "source_type": "episode",
      "locator": "S01",
      "retrieved_at": "2026-01-01T00:00:00Z",

    {
      "id": "evidence:dexter_s01e12_scene_45",
      "label": "Dexter confronts Brian in the shipping container",
      "episode_id": "dexter:s01e12",
      "source_id": "source:dexter_s01",
      "text": "Dexter slices Brian's throat with a scalpel.",

      "content_hash": "sha256:abc123...",
      "visible_from_order": 12,
```

**Claims projected as edges:** Each visible claim produces a `GraphEdge` in the response's `edges` array with a `claim_id` referencing the source claim. Structural edges (`PART_OF`, `PRECEDES`, `OCCURRED_IN`) have `claim_id: null` and `origin: "canonical"`.

**Concurrent queries:** The backend runs **7 concurrent Cypher queries** via `asyncio.gather()`: series metadata, visible nodes, structural edges, visible claims, user-authored relationships, sources, and evidence.

**Edge closure invariant:** Every returned edge has both `source` and `target` present in the `nodes` array. Dangling edges trigger a server-side validation error.

**Errors:** `404 series_not_found`, `422 invalid_visible_until_order`, `503 database_unavailable`

## 8. User Notes

User notes are plain-text annotations attached to a `Character` or `Claim` node. Notes inherit visibility from their target.

### 8.1 POST /api/series/{series_id}/notes

Create a user note attached to one `Character` or `Claim`.

**Path parameters:**

| Parameter | Type | Description |
|---|---|---|
| `series_id` | string | Series identifier |

**Request body:**

```json
{
  "target_type": "Character",
  "target_id": "dexter:character:dexter_morgan",
  "content": "Remember this detail."
}
```

| Field | Type | Constraints |
|---|---|---|
| `target_type` | string | `"Character"` or `"Claim"` |
| `target_id` | string | Must reference an existing node in the same series, 1–255 chars |
| `content` | string | Plain text, 1–4000 characters; rich text not supported |

**Server-owned fields (rejected if sent by client):** `id`, `series_id`, `origin`, `visible_from_order`, `created_at`, `updated_at`

**201 response:**

```json
{
  "id": "user-note:2a1f4c7e",
  "series_id": "series:dexter",
  "target_type": "Character",
  "target_id": "dexter:character:dexter_morgan",
  "content": "Remember this detail.",
  "origin": "user",
  "visible_from_order": 1,
  "created_at": "2026-07-29T10:00:00Z",
  "updated_at": "2026-07-29T10:00:00Z"
}
```

**Errors:** `404 resource_not_found`, `409 resource_conflict`, `422 invalid_request`, `503 database_unavailable`

### 8.2 GET /api/series/{series_id}/notes

List visible user notes for a series.

**Path parameters:**

| Parameter | Type | Description |
|---|---|---|
| `series_id` | string | Series identifier |

**Query parameters:**

| Parameter | Type | Required | Description |
|---|---|---|---|
| `visible_until_order` | integer (gt=0) | **Yes** | Spoiler boundary |
| `target_type` | string | No | Filter: `"Character"` or `"Claim"`. Must be paired with `target_id`. |
| `target_id` | string | No | Filter: target node ID. Must be paired with `target_type`. |

**Filter constraint:** `target_type` and `target_id` must be provided together or omitted together. Providing only one returns `422 invalid_request`.

**200 response:** Ordered by `updated_at` descending, then `id` ascending.

```json

  {
    "id": "user-note:2a1f4c7e",
    "series_id": "series:dexter",

    "updated_at": "2026-07-29T10:00:00Z"
  }
]
```

**Errors:** `404 resource_not_found`, `422 invalid_visible_until_order`, `422 invalid_request`, `503 database_unavailable`

### 8.3 GET /api/series/{series_id}/notes/{note_id}

Get a single visible user note.

**Path parameters:**

| Parameter | Type | Description |
|---|---|---|

## 10. Custom Relationships

Custom relationships are user-authored edges connecting two nodes via an allowed predicate. They are stored as `Claim` nodes with `claim_type: 'user_authored'` and projected as `GraphEdge` entries in the graph response.

**Allowed predicates (16 types):**

| Group | Predicates |
|---|---|
| Participation | `PARTICIPATED_IN`, `WITNESSED`, `CAUSED`, `AFFECTED`, `TARGETED`, `MENTIONED` |
| Character | `KNOWS`, `FAMILY_OF`, `WORKS_WITH`, `TRUSTS`, `DISTRUSTS`, `HELPS`, `OPPOSES`, `THREATENS`, `ATTACKS`, `KILLS` |

### 10.1 POST /api/series/{series_id}/custom-relationships

**Request body:**

```json
{
```

## 11. Revisions

Revisions are an append-only log of every mutation made to user content. Each revision captures the action (`Created`, `Updated`, `Deleted`, or `Reverted`) with before/after JSON snapshots. Revisions are spoiler-filtered by the same `visible_from_order` mechanism used by the graph.

### 11.1 GET /api/series/{series_id}/revisions

List visible revisions, most-recent-first.

**Path parameters:** `series_id` | **Query:** `visible_until_order` (required), `resource_type` (optional), `resource_id` (optional)

**200 response:**
```json
[{"id":"revision:abc123","series_id":"series:dexter","resource_type":"UserNote","resource_id":"user-note:2a1f4c7e","action":"Updated","before":{"content":"old"},"after":{"content":"new"},"created_at":"2026-07-30T12:00:00Z","visible_from_order":1}]
```

**Errors:** `422`, `503`

### 11.2 GET /api/series/{series_id}/revisions/{revision_id}

Get one revision. Hidden (beyond boundary) returns 404 same as missing.

**Errors:** `404`, `422`, `503`

### 11.3 POST /api/series/{series_id}/revisions/{revision_id}/revert

Restore resource to the state in the revision. Creates a new `Reverted` revision — history never destroyed.

| Action | Behavior |
|--------|----------|
| `Updated` | Restores properties from `before` snapshot |
| `Deleted` | Re-creates node from `before` snapshot (restores `REFERS_TO` for notes) |
| `Created` | Rejected — 422 `cannot_revert_create` |
| Canonical origin | Rejected — 409 `cannot_revert_canonical` |

**200 response:** The newly created `Reverted` revision.

**Errors:** `404`, `409`, `422`, `503`

## 12. Error Contract

All error responses use a single envelope:

```json
{
  "detail": {
    "code": "resource_not_found",
    "message": "Resource not found."
  }
}
```

### Stable Error Codes

| Status | Code | When |
|---|---|---|
| 401 | `unauthenticated` | No valid session cookie |
| 401 | `authentication_failed` | Google token verification failed (expired, invalid signature, wrong audience) |
| 401 | `auth_disabled` | Google Sign-In is not configured (`GOOGLE_CLIENT_ID` is empty) |
| 404 | `series_not_found` | Series lookup returned no result |
| 404 | `resource_not_found` | Hidden or absent resource (notes, custom nodes, custom relationships) |
| 409 | `resource_conflict` | Ownership violation or dependency conflict (e.g., deleting a node with notes) |
| 409 | `constraint_violation` | Neo4j constraint violation (e.g., duplicate unique ID) |
| 422 | `invalid_request` | General validation failure (Pydantic or repository-level) |
| 422 | `invalid_visible_until_order` | Missing, zero, negative, or non-persisted spoiler boundary |
| 503 | `database_unavailable` | Neo4j unreachable, connection refused, or auth error |

### Error Handling Rules

- **No detail leakage:** Error messages are generic. Database details, Cypher queries, credentials, hidden labels, and counts are never returned.
- **Sanitized validation errors:** `RequestValidationError` always returns 422 with a generic `"invalid_request"` — field names and validation specifics are never exposed.
- **Hidden direct reads are indistinguishable from 404:** A resource that exists but is behind the spoiler boundary returns the same `resource_not_found` envelope as a truly absent resource.
- **Database errors always 503:** `ServiceUnavailable`, `AuthError`, `ClientError`, and `Neo4jError` all map to 503 with a generic message.

## 13. Spoiler Boundary

### How It Works

Every story-sensitive entity in the graph carries a `visible_from_order` integer field representing the earliest episode order at which it's visible (no longer a spoiler). The `visible_until_order` query parameter represents how far the user has watched.

The backend applies a universal Cypher filter:

```cypher
WHERE entity.visible_from_order <= $visible_until_order
```

### Affected Endpoints

Every GET that reads story-sensitive content **requires** `visible_until_order`:

| Endpoint | Query Parameter |
|---|---|
| `GET /api/series/{id}/graph` | `?visible_until_order={order}` |
| `GET /api/series/{id}/notes` | `?visible_until_order={order}` |
| `GET /api/series/{id}/notes/{note_id}` | `?visible_until_order={order}` |
| `GET /api/series/{id}/custom-nodes/{node_id}` | `?visible_until_order={order}` |
| `GET /api/series/{id}/custom-relationships/{rel_id}` | `?visible_until_order={order}` |

### Validation Rules

| Condition | Response |
|---|---|
| Missing parameter | `422 invalid_visible_until_order` |
| Zero or negative value | `422 invalid_visible_until_order` |
| Positive integer not matching any persisted episode order | `422 invalid_visible_until_order` |
| Valid boundary | Filtered response |

### Fail-Closed Behavior

- Every entity in a query chain (claim → subject → object → evidence → source) must individually satisfy the visibility filter.
- Direct reads of hidden resources return indistinguishable `404 resource_not_found` responses.
- Collection responses contain no counts or metadata.
- Create endpoints have **no boundary parameter** — the server derives visibility from the referenced entities.

### Claim Temporal Validity

Claims also support optional time-bounded visibility:

```cypher
AND (claim.valid_from_order IS NULL OR claim.valid_from_order <= $visible_until_order)
AND (claim.valid_until_order IS NULL OR claim.valid_until_order >= $visible_until_order)
```

### PATCH Boundary Limitation

PATCH routes (`notes/{id}`, `custom-nodes/{id}`, `custom-relationships/{id}`) have no `visible_until_order` parameter. They enforce API ownership and immutable fields but do not perform spoiler filtering. The frontend must not treat a PATCH response as a spoiler-sensitive read.

## 15. Session Cookie Contract

After successful authentication, the server sets an HttpOnly session cookie:

| Attribute | Value | Notes |
|---|---|---|
| `HttpOnly` | `true` | Not accessible to JavaScript |
| `Secure` | Configurable via `SESSION_COOKIE_SECURE` | `false` in local dev, `true` in production |
| `SameSite` | `Lax` | Baseline CSRF protection |
| `Path` | `/` | Sent on all requests to the origin |
| Name | Configurable via `SESSION_COOKIE_NAME` | Default: `session` |
| Value | Opaque random session token | 48-byte `secrets.token_urlsafe`; no user info embedded |

### Session Management

- **Storage:** In-memory (swap for Redis in production via the `SessionRepository` protocol)
- **Token hashing:** Raw token is SHA-256 hashed before storage; raw token never persisted or logged
- **TTL:** Configurable via `SESSION_TTL_SECONDS` (default: 604800 = 7 days)
- **Expiry:** Lazy — checked on read; no background sweep
- **Revocation:** `POST /api/auth/logout` removes the session from the repository

### CSRF Strategy

- Baseline: `SameSite=Lax` on cookies
- State-changing requests must originate from a configured CORS frontend origin
- Future: state-changing endpoints should require a custom `X-Requested-With: XMLHttpRequest` header as a secondary check

## 16. Origin System

Every entity carries an `origin` field with exactly three possible values:

| Value | Meaning | Visual Treatment |
|---|---|---|
| `"canonical"` | Curated seed data (authoritative) | Solid borders |
| `"candidate"` | Automatically extracted, not yet reviewed | Dashed borders |
| `"user"` | User-created content (notes, nodes, relationships) | Dashed borders |

The `origin` field is the **only** discriminator — do not introduce `is_custom`, `source_type`, or any parallel boolean flag. Server-owned fields (`id`, `series_id`, `origin`, `visible_from_order`, `timestamps`) are never accepted from clients.

### S.2 Candidate Claims (Extraction Review)

Source: `backend/app/api/candidates.py`, prefix
`/api/series/{series_id}/candidates`. Candidate claims are `Claim` nodes with
`origin: 'candidate'` produced by ingesting a future extractor's output; this
route group lets a reviewer list, edit, approve (promote to canonical), or
reject them. Unlike most of this API, these routes are **not** behind
`CurrentUserDependency` — no session cookie is required.

#### POST /api/series/{series_id}/candidates/ingest

Ingest a batch of extraction claims as candidate claims. Body is an
`ExtractionBatchEnvelope` (`backend/app/domain/extraction.py`).

**Request body:**

```json
{
  "extractor_name": "dexter-extractor-v0",
  "extractor_version": "0.1.0",
  "run_timestamp": "2026-07-30T10:00:00Z",
  "claims": [
    {
      "schema_version": "0.1",
      "subject_id": "character:dexter",
      "predicate": "conceals",
      "object_id": "object:blood_slides",
      "claim_type": "observed_event",
      "confidence_level": "high",
      "relationship_effect": "strengthens",
      "visible_from_order": 1,
      "valid_from_order": 1,
      "valid_until_order": null,
      "evidence_text": "Dexter keeps his blood slides carefully organized in a hidden box.",
      "evidence_locator": "S01E01:12:34",
      "source_type": "transcript",
      "source_locator": "https://opensubtitles.org/dexter-s01e01",
      "episode_id": "episode:dexter:s01e01"
    }
  ]
}
```

**200 response:**

```json
{
  "created": ["extracted:a1b2c3d4e5f6g7h8"],
  "errors": []
}
```

**Note:** Returns `200` (not `201`) even though it creates resources — a
partial-batch result (`created` + `errors` arrays) doesn't map cleanly to a
single-resource `201 Created`. Each candidate's ID (`candidate_id`) is a
deterministic SHA-256 hash of its normalized content, making re-ingestion of
an identical claim idempotent.

**Errors:** `422 invalid_extraction_payload` (batch or per-claim validation failure — includes the failing claim's index and reason in `message`)

#### GET /api/series/{series_id}/candidates

List all candidate claims for a series.

**Query parameters:** `visible_until_order` (integer, optional — unlike the
main graph endpoint, this filter is **optional** here; omitting it returns
candidates at every visibility level, since this is a reviewer-facing
endpoint, not an end-user spoiler-safe read).

**200 response:** Array of claim dicts (same shape as `GraphClaim`, plus
`schema_version` and `created_at`).

#### GET /api/series/{series_id}/candidates/{claim_id}

Get one candidate claim by ID.

**200 response:** Single claim dict.

**Errors:** `404 candidate_not_found`

#### POST /api/series/{series_id}/candidates/{claim_id}/approve

Promote a candidate claim to canonical (`status: 'canonical'`). Logs an

**200 response:**

```json

  "status": "canonical",
  "origin": "candidate",
  "revision_id": "revision:9f8e7d6c5b4a"
}
```

**Note:** `origin` stays `"candidate"` after approval — only `status`
transitions to `"canonical"`. Approving does not change the claim's `origin`
field (see [Origin System](#16-origin-system); this is intentional per the

**Errors:** `404 candidate_not_found`, `409 cannot_approve_non_candidate` (claim's `origin` is not `"candidate"`), `422 invalid_extraction_payload`

### S.4 Change Sets (Chat-Driven Graph Mutations)

Source: `backend/app/api/change_set.py`, prefix
`/api/series/{series_id}/change-sets`. A `ChangeSet` is a typed, closed batch
of graph mutation operations proposed by the chat agent — the LLM never
executes a write directly. Propose (Stage 1) validates and persists only the
draft; confirm (Stage 2) re-validates everything fresh and applies the whole
batch in one Neo4j write transaction. All routes require an authenticated
session.

**Closed operation set (13 types, `operation_type` discriminator):**
`create_node`, `update_node`, `delete_node`, `create_relationship`,
`update_relationship`, `delete_relationship`, `create_claim`, `update_claim`,
`delete_claim`, `attach_evidence`, `create_note`, `update_note`,
`delete_note`. An `operation_type` outside this set — or any extra field on
an operation model — is rejected by Pydantic before any repository/Cypher
code runs.

#### POST /api/series/{series_id}/change-sets

Propose a ChangeSet (Stage 1). No target node/relationship/claim is mutated
here — only the `ChangeSet` draft resource itself is written.

**Request body:**

```json
{
  "series_id": "series:dexter",
  "chat_session_id": "chat-session:2a1f4c7e",
  "summary": "Add a custom relationship between Dexter and Debra",
  "operations": [
    {
      "operation_type": "create_relationship",
      "source_id": "dexter:character:dexter_morgan",
      "target_id": "dexter:character:debra_morgan",
      "relationship_type": "FAMILY_OF",
      "episode_id": "dexter:s01e01"
    }
  ]
}
```

**201 response:**

```json
{
  "id": "change-set:2a1f4c7e",
  "user_id": "user:abc123",
  "series_id": "series:dexter",
  "chat_session_id": "chat-session:2a1f4c7e",
  "status": "awaiting_confirmation",
  "visible_until_order_snapshot": 12,
  "summary": "Add a custom relationship between Dexter and Debra",
  "operations": [
    {
      "operation_type": "create_relationship",
      "source_id": "dexter:character:dexter_morgan",
      "target_id": "dexter:character:debra_morgan",
      "relationship_type": "FAMILY_OF",
      "episode_id": "dexter:s01e01",
      "properties": null
    }
  ],
  "created_at": "2026-07-29T10:00:00Z",
  "confirmed_at": null,
  "applied_at": null,
  "revision_id": null,
  "idempotency_key": null
}
```

**Body/path consistency check:** The route returns `422 invalid_request` if
`payload.series_id` does not match the `series_id` path parameter.

**Errors:** `401 AUTH_UNAUTHENTICATED`, `404 resource_not_found` (missing progress or chat session), `422 invalid_request`

#### POST /api/series/{series_id}/change-sets/{change_set_id}/confirm

Confirm and apply a ChangeSet (Stage 2). Re-validates every operation fresh
and applies the entire batch in one write transaction. Confirming an
already-`applied` ChangeSet is a safe idempotent no-op (the original stored
result is returned).

**200 response:** Same `ChangeSetResponse` shape, with `status: "applied"`,
`confirmed_at`, `applied_at`, and `revision_id` populated.

**Stale-boundary protection:** If the series' progress boundary has since
been *lowered* below the boundary this ChangeSet was proposed at, confirm is
rejected rather than silently applied.

**Errors:** `401 AUTH_UNAUTHENTICATED`, `404 resource_not_found`, `409 changeset_stale` (progress boundary lowered since propose), `409 resource_conflict` (already resolved — rejected/failed/reverted), `422 invalid_request` (an operation is no longer valid on re-validation)

#### POST /api/series/{series_id}/change-sets/{change_set_id}/reject

Reject a ChangeSet. Zero graph mutation; cannot be confirmed afterward.

**200 response:** `ChangeSetResponse` with `status: "rejected"`.

**Errors:** `401 AUTH_UNAUTHENTICATED`, `404 resource_not_found`, `409 resource_conflict` (already resolved)

#### POST /api/series/{series_id}/change-sets/{change_set_id}/revert

Revert a previously **applied** ChangeSet's create-shaped operations —
deletes every resource it created, restoring pre-apply state, and logs a new
`Reverted` revision (the original apply-time revision is never edited or
deleted).

**200 response:** `ChangeSetResponse` with `status: "reverted"`.

**Revert scope limitation:** Only ChangeSets whose operations are **entirely
create-shaped** support revert — an update/delete-shaped operation has no
stored prior state to restore.

**Errors:**

| Status | Code | When |
|---|---|---|
| 401 | `AUTH_UNAUTHENTICATED` | No session |
| 404 | `resource_not_found` | ChangeSet missing |
| 409 | `resource_conflict` | No applied revision to revert |
| 409 | `resource_conflict` | A resource this ChangeSet created was modified/removed by a later unrelated change (revert aborted rather than overwrite it) |
| 422 | `invalid_request` | ChangeSet contains a non-create-shaped operation (unsupported for revert) |

### S.5 LLM Settings

Source: `backend/app/api/settings.py`, prefix `/api/settings`. Lets the
authenticated user configure the LLM provider used by chat, persisted in
Neo4j (`:AppSetting {key: 'llm'}`) so it can be set from the UI without
editing `.env`. **The API key is write-only** — it is never returned in full
by any response, and never logged.

#### GET /api/settings/llm

Get the effective LLM configuration, with the key masked.

**200 response:**

```json
{
  "provider": "gemini",
  "model": "gemini-2.0-flash",
  "base_url": null,
  "enabled": true,
  "system_prompt_language": "english",
  "api_key_configured": true,
  "api_key_masked": "••••1234"
}
```

**Masking rule:** `api_key_masked` shows only the last 4 characters
(`"••••" + key[-4:]`); a key of 4 characters or fewer is fully masked
(`"••••"`, one bullet per character). `api_key_masked` is `null` when no key
is configured.

**Errors:** `401 AUTH_UNAUTHENTICATED`

#### PUT /api/settings/llm

Update the LLM provider configuration.

**Request body:**

```json
{
  "provider": "gemini",
  "api_key": "sk-...",
  "base_url": null,
  "model": "gemini-2.0-flash",
  "enabled": true,
  "system_prompt_language": "english"
}
```

| Field | Type | Constraints |
|---|---|---|
| `provider` | string | `"gemini"` or `"openai_compatible"`; default `"gemini"` |
| `api_key` | string or null | Max 4096 chars. **Blank/omitted keeps the previously stored key** — since GET never returns the full key, a client that only ever sees the masked form can update provider/model without clobbering the secret. |
| `base_url` | string or null | Max 2048 chars |
| `model` | string or null | Max 256 chars |
| `enabled` | boolean or null | `null` keeps the previously stored value. When effectively `false`, every chat/retrieval endpoint returns `503 LLM_DISABLED`. |
| `system_prompt_language` | string | `"english"` or `"turkish"`; controls which system prompt language the GraphRAG agent receives |

**200 response:** Same shape as `GET`.

**Errors:** `401 AUTH_UNAUTHENTICATED`
