## 1. Overview

HD Graf Cehennemi exposes a RESTful HTTP API backed by a Neo4j graph database. All data is **series-scoped** — every route that reads or writes story content requires a `series_id` path parameter.

The core architectural invariant is **spoiler-aware access**: every story-sensitive read requires a `visible_until_order` query parameter that represents how far the user has watched. The backend applies Cypher-level visibility filtering so the frontend never receives data it would need to hide.

**21 HTTP operations over 15 unique path templates** (including `/health`).

## 3. Authentication

Authentication is optional in development. When `GOOGLE_CLIENT_ID` is configured, Google Sign-In provides user identity via ID token verification.

### 3.1 POST /api/auth/google

Sign in with a Google ID token. Verifies the token signature, issuer, audience (`GOOGLE_CLIENT_ID`), and expiration. Creates or updates a local user record keyed on Google's `sub` claim. Sets an HttpOnly session cookie on success.

**Request body:**

```json
{
  "credential": "<Google ID token (JWT)>"
}
```

**200 response:**

```json
{
  "user": {
    "id": "user:abc123",
    "google_sub": "1234567890",
    "email": "user@example.com",
    "display_name": "Test User",
    "avatar_url": "https://lh3.googleusercontent.com/...",
    "created_at": "2026-01-01T00:00:00Z",
    "updated_at": "2026-01-01T00:00:00Z"
  }
}
```

**Errors:** `401 authentication_failed`, `401 auth_disabled`, `422 invalid_request`

### 3.2 GET /api/auth/me

Read the session cookie and return the currently authenticated user.

**200 response:**

```json
{
  "user": {
    "id": "user:abc123",
    "google_sub": "1234567890",
    "email": "user@example.com",
    "display_name": "Test User",
    "avatar_url": "https://lh3.googleusercontent.com/...",
    "created_at": "2026-01-01T00:00:00Z",
    "updated_at": "2026-01-01T00:00:00Z"
  }
}
```

**Errors:** `401 unauthenticated`

### 3.3 POST /api/auth/logout

Invalidate the server-side session and clear the cookie. Always returns 204 even if no valid session exists.

**Response:** `204 No Content` (no body)

      "status": "canonical",
      "confidence_level": "verified",
      "relationship_effect": 1.0,

  "sources": [
    {
      "id": "source:dexter_s01",
      "label": "Dexter Season 1",
      "episode_id": "dexter:s01e01",
      "source_type": "episode",
      "locator": "S01",
      "retrieved_at": "2026-01-01T00:00:00Z",

    {
      "id": "evidence:dexter_s01e12_scene_45",
      "label": "Dexter confronts Brian in the shipping container",
      "episode_id": "dexter:s01e12",
      "source_id": "source:dexter_s01",
      "text": "Dexter slices Brian's throat with a scalpel.",

      "content_hash": "sha256:abc123...",

**Claims projected as edges:** Each visible claim produces a `GraphEdge` in the response's `edges` array with a `claim_id` referencing the source claim. Structural edges (`PART_OF`, `PRECEDES`, `OCCURRED_IN`) have `claim_id: null` and `origin: "canonical"`.

**Concurrent queries:** The backend runs **7 concurrent Cypher queries** via `asyncio.gather()`: series metadata, visible nodes, structural edges, visible claims, user-authored relationships, sources, and evidence.

**Edge closure invariant:** Every returned edge has both `source` and `target` present in the `nodes` array. Dangling edges trigger a server-side validation error.

**Errors:** `404 series_not_found`, `422 invalid_visible_until_order`, `503 database_unavailable`

## 8. User Notes

User notes are plain-text annotations attached to a `Character` or `Claim` node. Notes inherit visibility from their target.

### 8.1 POST /api/series/{series_id}/notes

Create a user note attached to one `Character` or `Claim`.

**Path parameters:**

| Parameter | Type | Description |
|---|---|---|
| `series_id` | string | Series identifier |

**Request body:**

```json
{
  "target_type": "Character",
  "target_id": "dexter:character:dexter_morgan",
  "content": "Remember this detail."
}
```

| Field | Type | Constraints |
|---|---|---|
| `target_type` | string | `"Character"` or `"Claim"` |
| `target_id` | string | Must reference an existing node in the same series, 1–255 chars |
| `content` | string | Plain text, 1–4000 characters; rich text not supported |

**Server-owned fields (rejected if sent by client):** `id`, `series_id`, `origin`, `visible_from_order`, `created_at`, `updated_at`

**201 response:**

```json
{
  "id": "user-note:2a1f4c7e",
  "series_id": "series:dexter",
  "target_type": "Character",
  "target_id": "dexter:character:dexter_morgan",
  "content": "Remember this detail.",
  "origin": "user",
  "visible_from_order": 1,
  "created_at": "2026-07-29T10:00:00Z",
  "updated_at": "2026-07-29T10:00:00Z"
}
```

**Errors:** `404 resource_not_found`, `409 resource_conflict`, `422 invalid_request`, `503 database_unavailable`

### 8.2 GET /api/series/{series_id}/notes

List visible user notes for a series.

**Path parameters:**

| Parameter | Type | Description |
|---|---|---|
| `series_id` | string | Series identifier |

**Query parameters:**

| Parameter | Type | Required | Description |
|---|---|---|---|
| `visible_until_order` | integer (gt=0) | **Yes** | Spoiler boundary |

**Errors:** `404 resource_not_found`, `422 invalid_visible_until_order`, `422 invalid_request`, `503 database_unavailable`

## 10. Custom Relationships

Custom relationships are user-authored edges connecting two nodes via an allowed predicate. They are stored as `Claim` nodes with `claim_type: 'user_authored'` and projected as `GraphEdge` entries in the graph response.

**Allowed predicates (16 types):**

| Group | Predicates |
|---|---|
| Participation | `PARTICIPATED_IN`, `WITNESSED`, `CAUSED`, `AFFECTED`, `TARGETED`, `MENTIONED` |
| Character | `KNOWS`, `FAMILY_OF`, `WORKS_WITH`, `TRUSTS`, `DISTRUSTS`, `HELPS`, `OPPOSES`, `THREATENS`, `ATTACKS`, `KILLS` |

### 10.1 POST /api/series/{series_id}/custom-relationships

Create a user-authored custom relationship.

**Request body:**

```json
{
  "source_id": "dexter:character:dexter_morgan",
  "target_id": "dexter:character:debra_morgan",

  "episode_id": "dexter:s01e01"

```

| Field | Type | Constraints |
|---|---|---|
| `source_id` | string | Must reference a valid node in the same series |
| `target_id` | string | Must reference a valid node in the same series |
| `predicate` | string | One of the 16 allowed predicates |

## 11. Error Contract

All error responses use a single envelope:

```json
{
  "detail": {
    "code": "resource_not_found",
    "message": "Resource not found."
  }
}
```

### Stable Error Codes

| Status | Code | When |
|---|---|---|
| 401 | `unauthenticated` | No valid session cookie |
| 401 | `authentication_failed` | Google token verification failed (expired, invalid signature, wrong audience) |
| 401 | `auth_disabled` | Google Sign-In is not configured (`GOOGLE_CLIENT_ID` is empty) |
| 404 | `series_not_found` | Series lookup returned no result |
| 404 | `resource_not_found` | Hidden or absent resource (notes, custom nodes, custom relationships) |
| 409 | `resource_conflict` | Ownership violation or dependency conflict (e.g., deleting a node with notes) |
| 409 | `constraint_violation` | Neo4j constraint violation (e.g., duplicate unique ID) |
| 422 | `invalid_request` | General validation failure (Pydantic or repository-level) |
| 422 | `invalid_visible_until_order` | Missing, zero, negative, or non-persisted spoiler boundary |
| 503 | `database_unavailable` | Neo4j unreachable, connection refused, or auth error |

### Error Handling Rules

- **No detail leakage:** Error messages are generic. Database details, Cypher queries, credentials, hidden labels, and counts are never returned.
- **Sanitized validation errors:** `RequestValidationError` always returns 422 with a generic `"invalid_request"` — field names and validation specifics are never exposed.
- **Hidden direct reads are indistinguishable from 404:** A resource that exists but is behind the spoiler boundary returns the same `resource_not_found` envelope as a truly absent resource.
- **Database errors always 503:** `ServiceUnavailable`, `AuthError`, `ClientError`, and `Neo4jError` all map to 503 with a generic message.

| Field | Type | Description |

| Field | Type | Description |

| `target` | string | Target node ID |

| `origin` | string | `"canonical"`, `"candidate"`, or `"user"` |
| `claim_id` | string or null | Source claim ID for narrative edges; `null` for structural edges |

### GraphClaim

| Field | Type | Description |
|---|---|---|

## 13. Spoiler Boundary

### How It Works

Every story-sensitive entity in the graph carries a `visible_from_order` integer field representing the earliest episode order at which it's visible (no longer a spoiler). The `visible_until_order` query parameter represents how far the user has watched.

The backend applies a universal Cypher filter:

```cypher
WHERE entity.visible_from_order <= $visible_until_order
```

### Affected Endpoints

Every GET that reads story-sensitive content **requires** `visible_until_order`:

| Endpoint | Query Parameter |
|---|---|
| `GET /api/series/{id}/graph` | `?visible_until_order={order}` |
| `GET /api/series/{id}/notes` | `?visible_until_order={order}` |
| `GET /api/series/{id}/notes/{note_id}` | `?visible_until_order={order}` |
| `GET /api/series/{id}/custom-nodes/{node_id}` | `?visible_until_order={order}` |
| `GET /api/series/{id}/custom-relationships/{rel_id}` | `?visible_until_order={order}` |

### Validation Rules

| Condition | Response |
|---|---|
| Missing parameter | `422 invalid_visible_until_order` |
| Zero or negative value | `422 invalid_visible_until_order` |
| Positive integer not matching any persisted episode order | `422 invalid_visible_until_order` |
| Valid boundary | Filtered response |

### Fail-Closed Behavior

- Every entity in a query chain (claim → subject → object → evidence → source) must individually satisfy the visibility filter.
- Direct reads of hidden resources return indistinguishable `404 resource_not_found` responses.
- Collection responses contain no counts or metadata.
- Create endpoints have **no boundary parameter** — the server derives visibility from the referenced entities.

### Claim Temporal Validity

Claims also support optional time-bounded visibility:

```cypher
AND (claim.valid_from_order IS NULL OR claim.valid_from_order <= $visible_until_order)
AND (claim.valid_until_order IS NULL OR claim.valid_until_order >= $visible_until_order)
```

### PATCH Boundary Limitation

PATCH routes (`notes/{id}`, `custom-nodes/{id}`, `custom-relationships/{id}`) have no `visible_until_order` parameter. They enforce API ownership and immutable fields but do not perform spoiler filtering. The frontend must not treat a PATCH response as a spoiler-sensitive read.

## 15. Session Cookie Contract

After successful authentication, the server sets an HttpOnly session cookie:

| Attribute | Value | Notes |
|---|---|---|
| `HttpOnly` | `true` | Not accessible to JavaScript |
| `Secure` | Configurable via `SESSION_COOKIE_SECURE` | `false` in local dev, `true` in production |
| `SameSite` | `Lax` | Baseline CSRF protection |
| `Path` | `/` | Sent on all requests to the origin |
| Name | Configurable via `SESSION_COOKIE_NAME` | Default: `session` |
| Value | Opaque random session token | 48-byte `secrets.token_urlsafe`; no user info embedded |

### Session Management

- **Storage:** In-memory (swap for Redis in production via the `SessionRepository` protocol)
- **Token hashing:** Raw token is SHA-256 hashed before storage; raw token never persisted or logged
- **TTL:** Configurable via `SESSION_TTL_SECONDS` (default: 604800 = 7 days)
- **Expiry:** Lazy — checked on read; no background sweep
- **Revocation:** `POST /api/auth/logout` removes the session from the repository

### CSRF Strategy

- Baseline: `SameSite=Lax` on cookies
- State-changing requests must originate from a configured CORS frontend origin
- Future: state-changing endpoints should require a custom `X-Requested-With: XMLHttpRequest` header as a secondary check

## 16. Origin System

Every entity carries an `origin` field with exactly three possible values:

| Value | Meaning | Visual Treatment |
|---|---|---|
| `"canonical"` | Curated seed data (authoritative) | Solid borders |
| `"candidate"` | Automatically extracted, not yet reviewed | Dashed borders |
| `"user"` | User-created content (notes, nodes, relationships) | Dashed borders |

The `origin` field is the **only** discriminator — do not introduce `is_custom`, `source_type`, or any parallel boolean flag. Server-owned fields (`id`, `series_id`, `origin`, `visible_from_order`, `timestamps`) are never accepted from clients.
